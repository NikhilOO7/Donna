01 · Orientation

What Donna Is & How To Read This

Donna is an AI meeting collaborator. Not a transcription tool that summarizes after the fact — a participant that prepares before the meeting, listens and contributes during it, and remembers after it. The product covers the full meeting lifecycle:

🔭 BEFORE

Describe the meeting in plain language → Donna structures it (goal, agenda, risks), researches the topics on the live web with source-credibility tiers, emails pre-reads and invites, and imports your calendar so meetings arrive pre-briefed.

🎙 DURING

Every spoken sentence fans out to nine live agents. Donna detects decisions, checks factual claims against the web, pulls relevant documents and past-meeting memories, tracks the agenda, watches talk-time balance — and pushes each insight as a card the moment it's ready. She can even speak high-signal nudges aloud.

🧠 AFTER

A structured summary with decisions (and the verbatim quotes that triggered them), persisted action items with lifecycle tracking, calendar exports, per-assignee follow-up emails — and everything is indexed into memory so future meetings recall "in March you decided…".

Questions this section answers What problem does Donna solve? Why is it architected as three phases?

The founding insight: meetings fail from misalignment — people arrive unprepared, decisions evaporate, and knowledge dies in transcripts nobody reads. Each phase attacks one of those failure modes, and each phase has fundamentally different latency and cost characteristics — which is exactly why the architecture splits into hot, warm and cold paths (Section 02).

How to read this document

  • Learning the shape of the system? Read 01–04 in order. They give you the map.
  • Building a RAG system? Sections 05–06 are a complete, honest treatment — including the finding that contextual embeddings alone don't beat naive RAG (the hybrid does).
  • Building agents? Sections 09–10 are the core: a streaming multi-agent supervisor with per-agent timeouts and cost gates, plus every agent's what/when/why/how.
  • Making it production-grade? Sections 13–17: tenancy, cost, evals, ops.
  • Short on time? Section 18 (war stories) teaches more per paragraph than anything else here — real bugs, root causes, and the principles they encode.
Conventions File paths like apps/api/services/meeting/agent_dispatcher.py refer to the repo. Badges mark cost tiers: free = no LLM call, fast = gpt-4o-mini, smart = gpt-4o, vision = vision-capable model. Every claim in this document is backed by code that exists and tests that pass (172 at last count).
02 · High-Level Design

The Whole System On One Page

Donna is a modular monolith + workers: one FastAPI backend holding the domain logic, three worker processes for everything latency-tolerant or long-running, five data/infra services, and a Next.js frontend. Ten containers total, one docker compose up.

The full system in the docs/diagrams visual language — successor to 01-architecture.svg. The hot/warm boxes inside the backend and the cold job-worker are the three temperature paths detailed below; the data-plane bus feeds five stores picked by access pattern.

The three temperature paths

The single most important architectural idea in Donna: work is routed by latency budget, not by feature. Ask of every piece of work: how fast must the user see the result?

PathBudgetWhat runs hereMechanism
HOT < 2s first result
< 12s LLM results		 Utterance → nine live agents → nudges asyncio.as_completed streaming fan-out, per-agent timeouts, regex cost-gates, Redis burst coalescing, slim SQL state loads
WARM < 50ms Fan-out of every event to every connected browser In-process MeetingHub + Redis pub/sub bridge across replicas; per-connection privacy filtering at the socket
COLD seconds–minutes Web research, summaries, document OCR/embedding, memory indexing, nightly re-scans Arq (Redis-backed job queue), job_timeout=600, cron at 04:10 UTC, BackgroundTasks fallback if Redis is down
Why a modular monolith instead of microservices? A meeting product's domain objects (meeting, transcript, nudge, decision) are deeply interrelated — splitting them into services would turn in-process function calls into network calls with distributed-transaction problems, for zero scaling benefit at this stage. The things that genuinely need process isolation are isolated: CPU-heavy document OCR (job-worker), audio streaming (voice-worker), and the conversational agent (assistant-worker) each run separately so they can never starve the API's event loop. The seams for a future split already exist — they're the router/service boundaries.
Q: Why do the workers import from apps/api? Deliberate. Workers reuse the same service layer, models, and config as the API — one source of truth for business logic. The cost is that worker images contain the whole app; the benefit is that a bugfix in, say, the summary pipeline applies everywhere with no version skew.

03 · Tech Stack

Every Technology, and Why It Won

Nothing here is "we used X because it's popular." Each row answers: what job does it do, and why this over the alternatives a beginner would reach for.

Q: Four datastores — isn't that over-engineering? Each store holds a different shape of the same knowledge, chosen by query pattern: rows you filter and join (Postgres), vectors you rank by similarity (Qdrant), edges you traverse (Neo4j), blobs you fetch whole (MinIO), plus Redis for everything ephemeral. Forcing one store to do all five jobs is how you get 500ms queries and un-debuggable data. The teaching point: pick stores by access pattern, not by fashion — and make the optional ones (Neo4j) actually optional in code.
04 · Data Model

The Schema — What Lives Where, and Why

Everything durable lives in PostgreSQL schema doc_intel, owned entirely by Alembic migrations. The models are SQLAlchemy 2.0 style (Mapped[] + mapped_column) — typed at the class level so a schema mistake is a type error, not a runtime surprise.

TableWhat it holdsDesign decisions worth learning

Agenda is JSONB items with per-item status so the agenda agent can flip pending→covered without a join table. external_event_id dedupes calendar imports. Soft-delete (deleted_at) because meetings anchor decisions you never want to orphan.

Dismiss/pin are timestamps, not booleans: they're feedback signals with a when, feeding the learning loop (§12).
decisionsText, owner, deadline, status, context, source_nudge_idTwo lineage fields tell the whole story: source_nudge_id = "the AI surfaced it", context = the verbatim conversation quotes that triggered it. Leadership can always see who said what.
action_itemsDescription, assignee, deadline, priority, status, optional decision_idStatus lifecycle (open→in_progress→done) is data, which is what makes the cross-meeting "open items" dashboard view a single query.

analytics eventsProduct metrics: nudge_created/accepted, queries, latenciesThe instrumentation that answers "what's the nudge acceptance rate?" — the founder metric.
Why JSONB for utterances/attendees/agenda but real tables for decisions/actions? The rule used throughout: if you filter, join, or update it row-by-row, it's a table; if you read it as a unit, it's JSONB. Transcripts are appended and read as windows — JSONB. Decisions are queried across meetings, status-updated individually, joined to action items — table. When JSONB data DOES need server-side computation, Postgres delivers: jsonpath slicing for transcript windows, jsonb_array_elements aggregation for talk-time stats.
Q: How do migrations stay honest? Three mechanisms: (1) every schema change is a hand-reviewed Alembic revision — the chain currently runs through f3a9d82c41b7 (calendar integration); (2) CI applies all migrations to a fresh Postgres and then runs alembic check, which fails if the models have drifted from the migration history; (3) production startup can optionally run alembic upgrade head, but the recommended pattern is a pre-deploy job — the app assumes schema, it doesn't create it.
05 · Knowledge Layer, Part 1

Document Intelligence Pipeline

Everything Donna "knows" from files enters through one pipeline: upload → parse → understand → chunk → embed → index. It runs off the API process (cold path) because OCR and layout analysis take seconds to minutes — and an API worker doing OCR is an API worker not answering requests.

The upload pipeline, in the same visual language as docs/diagrams/02-document-upload-pipeline.svg — updated for the job-queue cold path and warm worker container.

Upload & dedupe. apps/api/main.py → POST /api/v1/documents/upload — the file is hashed; an identical, successfully-processed document 409s, but a previously failed duplicate deletes the dead rows and reprocesses. The authenticated user becomes owner_id on the document AND inside every embedding's payload — tenancy starts at ingestion (§13). An optional meeting_id auto-attaches it as meeting material.
Off the API in under a second. The original goes to MinIO, a Document row is created with processing_status=processing, and process_document_job is enqueued. The HTTP response returns immediately — the browser polls status. If Redis is down, FastAPI BackgroundTasks picks it up in-process: degraded, never dropped.
Four ingestion agents run in the job-worker. apps/workers/job_worker.py — a module-level ServiceContainer is built once per worker process and reused across jobs, because Docling/EasyOCR model loading takes seconds and paying it per-document would dominate small files.
Chunking preserves structure. Chunks carry section paths and element types (text/table/image). Element type matters later: the context agent boosts table chunks for data-hungry questions.
Embed once, index everywhere. Three distinct vectors per chunk (§06), batched 96-at-a-time, upserted to Qdrant with deterministic UUIDv5 point IDs — re-processing a document overwrites instead of duplicating. Entities and relations mirror to Neo4j; the RAG response cache is invalidated because cached answers may now be stale.
Q: Why keep the original file in MinIO if we have the chunks? Because the pipeline improves. When chunking strategy or embedding model changes, you re-run ingestion from originals. Deleting sources would freeze you at your first — worst — version of the pipeline. Storage is the cheapest thing in this architecture.
06 · Knowledge Layer, Part 2

Embeddings, Retrieval & RAG — The Honest Version

This section teaches retrieval the way the codebase learned it — including the negative result most tutorials skip: contextual embeddings alone did not beat naive RAG. The measured win comes from fusing them with lexical search.

What "3-level contextual embeddings" actually means

A chunk's raw text often can't answer "what is this about?" on its own — "revenue grew 15%" means nothing without knowing it's from the Q3 board deck, section Financials. So each chunk is embedded three times, with three different context windows folded in (apps/api/services/document/contextual_processor.py):

LevelWeightContext folded into the embedded textWhat it's good at
Local50%The surrounding chunks (previous/next window)Precise passage-level matches
Document30%Document title + section path"In the vendor contract, what…" queries
Global20%Genuinely related other documents, found by a tenant-scoped Qdrant probe at ingestion timeCross-document connections

The three vectors are stored in three Qdrant collections (_local, _document, _global), and their average goes into _unified. Query time can search one level or fuse all of them with those weights.

The honest finding (measured, not vibed) The retrieval benchmark (tests/benchmarks/retrieval_eval.py, wired into the eval harness §16) runs three arms over a ground-truth corpus: naive dense RAG, contextual-dense, and contextual + BM25 hybrid. Result: contextual embeddings alone under-perform naive dense retrieval — folding shared context into every chunk homogenizes chunks within a document. The hybrid, which fuses the contextual dense ranking with lexical BM25 via Reciprocal Rank Fusion, is what wins: MRR 0.93 vs 0.85 baseline (+0.08), Recall@1 +0.11. The eval gate now requires that lift to persist. Lesson: measure your retrieval; the fancy technique is not automatically the better one.

Query-time flow. The same retrieval core serves the API, the in-meeting context agent, the assistant panel, and the MCP server.

The caching layers, and why each exists

CacheTTLKeyWhy
Embedding cache24hsha256(model:text)Embeddings are deterministic per model+text — repeats (nudge re-scans, burst dispatches, common questions) should never pay OpenAI twice. Values are float32-packed + base64: ~4× smaller than JSON float lists, and text-safe because the Redis client runs decode_responses=True (§18).
RAG response cache5 minsha256(owner:query:level)Short because answers go stale when documents change (uploads invalidate it). The owner is in the key because retrieval is tenant-scoped — the same question has different correct answers per user, and an owner-less key is a cross-tenant leak (§18).

Q: What exactly is in a "source" the user sees? build_citation() (apps/api/services/rag/rag_service.py) normalizes provenance across knowledge types: a document chunk renders as "filename · section · page"; a meeting memory renders as "Meeting: title (date)" plus the verbatim quote. Provenance is part of the data contract at indexing time — not a UI afterthought — which is why every surface (nudges, assistant, MCP tools) can cite without re-deriving anything.
07 · Meeting Lifecycle, Phase 1

BEFORE — Prep, Research, Invites, Calendar

The BEFORE phase turns "I have a meeting Thursday" into a structured, researched, pre-briefed event — with as little typing as possible. Three setup modes, one research pipeline, and three ways meetings arrive without being created by hand.

Three ways to create a meeting

📝 Standard Setup

Classic form — but with Smart Fill: free-text like "prepping a session with engineers to ship the component on time, I'm in product design" hits the prep agent and pre-fills title, type, goal and agenda items.

💬 Conversational Setup

A chat loop with the prep agent. Each message refines the same structured prep JSON — live preview builds on the right, Confirm & Create when it looks right. The previous JSON is passed back each turn so refinement is incremental, not start-over.

📄 Upload Transcript

Paste an existing transcript → parsed into speaker-attributed utterances → a completed meeting is created and the summary pipeline runs on it. Instant value with zero live usage — the cold-start demo.

Why a structured "prep contract"? The prep agent (apps/api/services/meeting/prep_agent.py, fast) returns exactly {role, meeting_type, meeting_goal, agenda_items[], risks_or_tensions[], confidence_notes} — few-shot prompted, JSON-only, then normalized in code (length caps, list caps, type coercion). The lesson for agent builders: never trust LLM output shape — prompt for a contract, then enforce it mechanically. confidence_notes implements human-in-the-loop honestly: the agent says what it inferred vs. what you told it.

The research pipeline (cold path)

The research pipeline — successor to docs/diagrams/04-research-pipeline.svg, now with urgency ranking, blind spots, and the retention loop.

Q: Why credibility tiers instead of just top search results? Because the product's promise is "trace the claim." Tier 1 = primary/authoritative (official docs, filings, peer-reviewed), Tier 2 = reputable secondary, Tier 3 = everything else. The tier renders on every source chip in the UI, the synthesis prompt sees tier labels, and fact-check nudges quote the tier. Users learn to trust the green chips — which is the entire game for an AI that asserts things mid-meeting.

Meetings that create themselves

  • Google Calendar sync (§15) imports the next 7 days of events as meetings — title, attendees, schedule — deduped by external_event_id.
  • Email-in (§15): mail a question to Donna's inbound address → a research-request meeting is created, the pipeline runs, you get a confirmation with the link.
  • The nightly cron (04:10 UTC) finds meetings scheduled within 48h that lack a fresh brief — including calendar imports — and researches them overnight. Together these close the cold-start problem: you wake up to prepared meetings you never configured.
Also in this phase Invite emails with the meeting link + a real .ics attachment (RFC 5545 generated in ~100 lines of dependency-free code — apps/api/services/meeting/ics.py); attendee expertise capture (feeds activation nudges §10); meeting-scoped document attachment (boosts retrieval §06); and the voice-setup wizard that verifies mics and registers who's in the room.
08 · Meeting Lifecycle, Phase 2a

The Real-Time Voice Pipeline

How spoken audio becomes text in the transcript, and how Donna's voice gets back into the room. This is the part beginners find most magical and most intimidating — broken down, it's five well-defined hops.

Both directions of audio — successor to 06-voice-chat-flow.svg and 09-tts-speakback.svg, now with interim ghost text and barge-in.

Q: Why one Deepgram stream per participant track instead of diarizing one mixed stream? Because LiveKit already knows who is speaking — each participant publishes their own track, so speaker attribution is free and perfect. Acoustic diarization is kept for the one case that needs it: a shared laptop in a conference room (diarize=conference labels utterances "Name — Speaker N" by majority word-speaker). Use identity when the transport gives it to you; infer it only when it doesn't.
Why do agents only run on finals, when interims exist? Interims re-transcribe the same words repeatedly as confidence improves — running nine agents on every revision would multiply cost by ~10 for zero insight gain. So interims go straight to the UI as ghost text (pure Redis publish, no DB write, throttled to 300ms per speaker), and finals — complete sentences — trigger persistence and the dispatcher. Both latency feel and cost discipline, no tradeoff.
Resilience details worth stealing Utterance POSTs retry with exponential backoff (0.5s→8s, 5 attempts, 4xx = no retry); the Deepgram websocket lives in a reconnect loop that buffers the in-flight audio frame across drops; TTS playback failure logs and abandons — a voice glitch must never take down transcription. Every external connection in this worker assumes it will fail sometimes.
09 · Meeting Lifecycle, Phase 2b

DURING — The Hot Path, Line By Line

This is the heart of Donna and the most instructive piece of engineering in the codebase: a streaming multi-agent supervisor. One utterance in, up to nine insights out — each delivered the instant its agent finishes, never waiting for the slowest.

The successor to docs/diagrams/07-five-agent-fan-out.svg — nine agents, streamed. Fast free agents (green) emit in milliseconds while fact-check is still searching the web.

Walking the code

Utterance lands. routers/meetings.py → POST /{id}/utterances — accepted from a user JWT or the voice worker's service key. The append takes a row lock on the transcript (concurrent speakers can't lose words), broadcasts utterance_added, then enqueues dispatch_job.
One cycle per meeting. agent_dispatcher.dispatch() takes a Redis distributed lock with wait=False. If a cycle is already running, it sets a pending flag and returns — the running cycle re-runs once over the newer state when it finishes (max 3 coalesced cycles). Rapid speech produces one catch-up pass, not a queue of stale duplicates.
State loads slim, connection releases fast. meeting_service.get_dispatch_state() issues targeted selects: owner, attendees, agenda, started_at, decision count, research topics, attached doc ids — and the transcript via a server-side jsonpath slice ($[last-11 to last]) so a 2-hour meeting ships 12 utterances, not 2,000. The session closes before the fan-out: holding a pooled connection through a 25-second agent cycle is how you exhaust a pool at ten concurrent meetings.
Nine tasks, streamed. Each agent is wrapped in _run_agent() — tracing span + asyncio.wait_for with its own budget. Then for fut in asyncio.as_completed(tasks): each finished agent's nudge is emitted immediately. The old design (gather) made a 200ms activation nudge wait for a 20s web search — the barrier was the bug.
Emit = suppress-check → persist → speak? → broadcast → metric. Each in its own short DB session. should_suppress consults the learned-mute stats (§12); _maybe_speak_nudge publishes to the TTS channel if the leader enabled voice and relevance ≥ 0.8 (2-min cooldown); the WS payload is built from the persisted row; a nudge_created analytics event records it for the acceptance-rate metric.
The supervisor pattern, generalized If you build one thing from this document, build this: N specialist agents · each with a free pre-check · each with a timeout · results streamed, not gathered · failures degrade to None. It gives you bounded latency (slowest useful agent, not slowest agent), bounded cost (most utterances never touch an LLM), and graceful partial failure (a Neo4j outage costs you connection nudges, not the meeting). Every design choice falls out of asking: what must never block what?

Phase 2 — Live meeting (9) hot

Ordered by timeout — which is also, by design, the order results tend to arrive.

Marks agenda items covered as they're discussed; nudges when the meeting runs long with items untouched.
How
Lexical: ≥50% of an item's content tokens (meeting-filler stopworded out) appearing in the recent window → covered. Persists status, broadcasts agenda_progress, reminder nudge only after 20+ utterances with a 10-min cooldown.
Why free
It runs on every cycle — an LLM here would be the single largest cost in the product for a task lexical matching handles (eval-verified, §16).
12 · FlowAgent free · 5s meeting/flow_agent.py
What
Meeting-flow awareness: live talk-time meter, "talk-time is getting one-sided", "30 minutes in — no decision logged yet".
How
Postgres aggregates per-speaker word counts from the JSONB transcript in one query (every 5th utterance); dominance = top share ≥ 65% with ≥2 speakers; decision-pace check uses started_at + decision count from dispatch state. All nudges Redis-cooldowned.
13 · MemoryAgent free · 6s meeting/memory_agent.py
What
Resurfaces past decisions when a settled topic comes back: "In the March meeting you decided…"
How
Matches live phrases against the Neo4j decision subgraph written by the summary pipeline. The retention loop's read side.
14 · KGQueryAgent free · 8s meeting/kg_query_agent.py
What
Live connection-finding: "Vendor X appears in your Q3 contract AND the security audit."
How
spaCy extracts entities from the utterance (model preloaded at startup so the first call doesn't stall the dispatcher); 1–2 hop Cypher traversal; nudge shows the path.
15 · ContextAgent free* · 10s meeting/context_agent.py
What
The RAG agent: relevant document chunks AND past-meeting memories for what's being discussed, with citations.
How
Query = last 3 utterances (skip if <20 chars); embedding usually served from cache (*that's the free), tenant-filtered Qdrant search; re-ranks with element-type boosts (tables win for numbers questions); meeting-attached documents get boosted, not filtered.
16 · ScribeAgent fast · 12s meeting/scribe_agent.py
What
Decision detection → "Sounds like a decision — want me to log it?" cards.
How
Regex gate for commitment language (eval-tuned: "consider it done" fires, "we should probably think" doesn't §16) → gpt-4o-mini extracts {decision, owner, deadline, confidence} → the card carries the verbatim trigger quotes, which become Decision.context on logging.
17 · InsightAgent fast · 12s meeting/insight_agent.py
What
Surfaces pre-meeting research the moment conversation touches its topic — the bridge between BEFORE and DURING.
How
Topical match of live discussion against the brief's topics; card cites finding + source + tier.
18 · FactCheckAgent fast ×2 + Exa · 25s meeting/fact_check_agent.py
What
Verifies checkable claims against the live web: verdict (supported / contradicted / partial / unverified) + quoted sources.
How
Claim-pattern gate (numbers, %, $, trends, superlatives, attribution — eval-tuned) → extraction call → Exa search → verdict call. Per-claim Redis cooldown so a repeated stat isn't re-checked. Longest timeout in the fleet because it's the only agent doing live web I/O — and streaming means nobody waits for it.

Why smart

12 · Meeting Lifecycle, Phase 3

AFTER — Summary, Memory, and the Compounding Loop

Ending the meeting is where most tools stop and where Donna's moat begins: everything the meeting produced becomes queryable, citable memory — and feedback signals tune the agents.

Successor to 08-memory-model.svg + 10-summary-pipeline.svg — the write side of Donna's memory.

Why memory is stored as four record types

  • Summary record — coarse recall: "what was that meeting about?"
  • Decision records — one per decision, carrying owner, status, and the verbatim trigger quotes. This is what lets a citation say who said what, months later.
  • Transcript windows — mid-granularity: catches discussions that never became formal decisions.
  • Extracted facts fast — atomic, standalone statements ("Vendor B includes support in enterprise tier") that embed and retrieve far better than raw dialogue.

All four flow through the same embedding + storage path as document chunks — which is the architectural decision that makes "search everything I know" a single Qdrant query instead of a federated mess. build_citation() branches on source_type to render provenance correctly either way.

Also in this phase Decision/action status lifecycles (click chips: open→in_progress→done) with a cross-meeting "Open Action Items" dashboard panel; .ics download of deadlines; per-meeting LLM cost readout (GET /{id}/cost, from the Redis meter §14); and transcript import — the whole AFTER pipeline works on meetings Donna never attended.
13 · Cross-Cutting Concern 1

Auth, Tenancy & Multiplayer

Donna is multi-tenant (users must never see each other's knowledge) and multiplayer (people in the same meeting see different things by role). Both boundaries are enforced server-side at every layer — never in the client.

Identity: three ways in

CallerCredentialMechanism
Browser userJWT Bearer tokenArgon2 password hashing → PyJWT tokens; Depends(require_user) resolves the user; WS connects pass the token as a query param, verified before the socket joins the hub
Workers (voice)Static service keyX-API-Key header; get_service_or_user accepts either identity on endpoints both call (utterances, /query) — service callers get unscoped access, humans get owner-scoped
Dev/demo modenoneREQUIRE_AUTH=false lets everything through as ownerless — every check is written as "if a user is present, enforce" so demos work without seeding accounts

Tenancy: the same rule at four layers

Rows. Meetings and documents carry owner_id. Access checks return 404, not 403 — a 403 confirms the resource exists, which is itself a leak.
Vectors. Every Qdrant point's payload carries owner_id written at ingestion; every search applies the filter. Retrieval isolation can't be bypassed by a clever query because it's in the index, not the endpoint.
Caches. The RAG response cache key includes the owner — a cached answer is as private as a live one (the bug that motivated this is §18).
Graph. Neo4j queries carry owner scoping in their match clauses.

Multiplayer: leader vs participant

👑 Leader (owner)

Full feed: every nudge from every agent, all controls (start/end, log decisions, pin/dismiss, voice toggle, emails). The role is derived — creator = leader — not stored redundantly.

🙋 Participant (invited by email)

Access via JSONB containment (their email in attendees). Sees the shared board: leader-pinned nudges plus activation nudges addressed to them personally. Enforced twice: _visible_nudges() on REST reads and _visible_to() per-socket on WS delivery.

Why pinning doubles as sharing The leader's pin gesture already means "this matters." Making pinned = shared gives multiplayer privacy a one-bit mental model instead of a permissions matrix — and activation nudges being private-by-default means Donna can tap a participant's shoulder ("this is your lane") without broadcasting it. The PDF's design, implemented at the socket layer.
14 · Cross-Cutting Concern 2

Cost Engineering — Why a Meeting-Hour Doesn't Bankrupt You

A naive implementation of "nine agents per utterance" pays for nine LLM calls per spoken sentence — a meeting-hour would cost dollars. Donna's typical utterance costs $0. Four mechanisms, in order of impact:

Deterministic gates before every model call. Regex/token matchers decide whether an LLM is even consulted: decision language for scribe, claim patterns for fact-check, similarity floors for insight, and six of nine hot agents never use an LLM at all. The gates are eval-tested with recall-biased floors (§16) — cheap must not mean blind.
Model tiering. MODEL_FAST (gpt-4o-mini, ~15× cheaper) for every structured extraction/classification — 14 of ~18 call sites. MODEL_SMART (gpt-4o) only for the three prose artifacts users actually read: research synthesis, meeting summary, RAG answers. MODEL_VISION for figures. All env-swappable — a model upgrade is config, not a refactor.
Caching. Embedding cache (24h, deterministic), RAG response cache (5min, owner-keyed), per-claim fact-check cooldowns, spoken-nudge cooldowns, dispatch burst coalescing. Repeat work is the silent cost killer; every repeat has a named cache.
Metering. Every LLM call records model + token usage into a per-meeting Redis hash in micro-USD (core/llm_meter.py), surfaced at GET /{id}/cost and as a UI chip. You cannot price a product on costs you don't measure — this is the input to unit economics, not an afterthought.

Integrations — Donna Beyond Her Own UI

Three doors into Donna that aren't the web app — each showing a different integration pattern worth learning: an MCP tool server, an inbound webhook, and a full OAuth flow.

1 · The MCP server — Donna as tools apps/mcp_server/server.py

The Model Context Protocol server exposes the knowledge substrate to any MCP client (Claude Desktop, Claude Code, IDEs) over stdio. Five read-only tools, every result cited:

ToolWhat it returns
search_knowledgeSemantic search over documents AND meeting memories — content + score + citation each

Design choices to copy: read-only (an external client mutating meetings is a different trust conversation), lazy singletons (embedder/store/RAG built once per process, not per tool call), and owner scoping via env (DONNA_MCP_OWNER_EMAIL applies the same row-level isolation as the API — unset means dev mode).

2 · Email-in research — the inbound webhook pattern apps/api/routers/integrations.py

Postmark POSTs inbound mail to /api/v1/integrations/email/inbound?token=… — a shared-secret query token gates the webhook (503 if unconfigured, 401 on mismatch).
Sender verification: only registered users may commission research. Unknown senders get a 200 + ignored — a 4xx would make Postmark retry spam forever. Webhooks acknowledge; they don't argue.
Subject/body → a research-request meeting, pipeline enqueued, confirmation email sent with the meeting link. "urgent/asap/today" in the subject is flagged in the reply.

3 · Google Calendar — the OAuth-read pattern apps/api/services/integrations/google_calendar.py

Consent URL built with access_type=offline (that's what yields a refresh token) and an HMAC-signed state (user_id.hmac(jwt_secret)) so the callback can't be replayed onto another account.
Callback verifies state, exchanges the code (plain httpx — no Google SDK dependency for two REST calls), stores the refresh token on the user row, bounces back to the dashboard.
Sync refreshes an access token, pulls 7 days of events, creates meetings — title, attendees, schedule — deduped by external_event_id. Cancelled events skipped, room-resource "attendees" filtered.
The payoff is composition: imported meetings fall inside the nightly research cron's 48-hour window — so calendar events become pre-briefed meetings with zero user action. Features multiply when they share primitives.
Feature-gating pattern All three doors are config-gated and honest about it: no Google credentials → endpoints return 503 "not configured" and the sidebar button hides; no inbound token → webhook 503s; MCP without an owner email → dev mode. Absent config is a first-class state, not a crash.
16 · Cross-Cutting Concern 4

The Eval Harness — Unit Tests for Intelligence

A prompt tweak or regex change can silently make the product dumber while every unit test stays green. The eval harness (evals/) closes that hole: golden datasets + metric floors, gated in CI — quality regressions fail the build.

What each suite grades

SuiteGradesNeeds
scribe_precheck / factcheck_precheckThe regex gates that decide when to pay for an LLM. Recall-biased floors: a missed decision costs more than a wasted call.nothing
activation / agenda_coverage / flowThe fully deterministic agents: right person activated, right items covered, right room-dynamics calls.nothing
retrievalIR metrics over the ground-truth corpus — and the lift gate: contextual+BM25 hybrid must keep beating naive dense RAG (MRR +0.03 floor).local embedder (offline)
scribe_llmThe LLM extraction behind the gate, on the same gate-filtered distribution production sees.OPENAI_API_KEY
Day one: the harness found three real bugs First run: fact-check recall 0.73, scribe 0.87. The failure IDs pointed at: (1) "$99" never matched the claim gate — a regex \b can't sit between a space and "$" (both non-word), so the currency alternative had silently never fired; (2) "consider it done" wasn't decision language but "we should probably think about it more" was; (3) agenda titles with filler ("Vendor selection") never matched real discussion. All fixed, floors ratcheted to 0.95, and the gates now hold in CI. An eval that finds nothing on day one is usually measuring the wrong thing.
The workflow this buys you Change an agent → run the suite → see exactly which golden cases you won or lost, by ID → fix or consciously accept → --update-baselines ratchets the floors. Datasets grow by appending JSONL lines — labeled by human judgment, deliberately including cases the implementation currently gets wrong. Honest datasets are the whole point.

Optional tracing (no-op when disabled). The dispatcher wraps each agent in a span — a slow cycle decomposes into per-agent timings instead of a mystery.

Resilience — the degradation ladder

FailureBehavior
OpenAI down / quota outCircuit breakers (core/resilience.py) trip after repeated failures; /health exposes breaker states; the frontend shows a global "intelligence degraded" banner. Transcripts, meetings, decisions all keep working — the product's spine is not the LLM.

CI — six gates on every push

Lint: ruff check + format verification.
Migration integrity: apply the full chain to a fresh Postgres, then alembic check for model drift.
Tests: 172 tests — unit, integration (real dispatcher against mocked agents), an end-to-end meeting lifecycle against real Postgres, and the WS fan-out benchmark with its latency assertion.
Eval gates: evals.run --suites deterministic --gate — agent-quality floors enforced like tests (§16).
Security audit: pip-audit against known CVEs.
Build check: compose config validation.
Q: What would horizontal scale look like? The design already assumes it: dispatch is serialized per-meeting by a distributed lock (not a process lock), WS fan-out crosses replicas via Redis pub/sub, job workers are stateless consumers you replicate freely, and sessions/caches live in shared stores. Scale the backend N×, the workers M×, and nothing changes but throughput. The single-writer spots (transcript row lock) are per-meeting, so they shard naturally.
18 · Wisdom

War Stories — Real Bugs, and the Principles They Encode

Every bug below actually happened in this codebase, was found by its own tests/evals/smoke runs, and got fixed the same day. Each teaches something a tutorial won't.

The config that silently wasn't Pydantic v2 ignores the v1-style Field(env="APP_ENV") kwarg — so APP_ENV=production in Docker had never actually set environment. When the fields were migrated to validation_alias=AliasChoices(...), production mode engaged for real for the first time — and immediately exposed a second latent bug: the engine builder combined NullPool with pool sizing kwargs, an invalid pairing that crashed on boot (and NullPool is wrong for an API anyway — a fresh TCP connection per checkout). Principles: deprecation warnings are load-bearing; and config that silently no-ops is worse than config that crashes.
The worker that couldn't reach the database — quietly Compose gave the job-worker DATABASE_URL, but the engine builds its DSN from POSTGRES_HOST/PORT/… parts. The worker connected to localhost inside its own container, failed, logged, and the dispatch job "completed." Found only by a live smoke test asserting on outcomes (did the agenda flip to covered?) rather than logs. Principles: know which env vars your code actually reads; and smoke tests must assert results, not absence of errors.
The cache that would have leaked between tenants The RAG response cache was keyed on query + context_level — correct when retrieval was global, silently wrong the day retrieval became owner-scoped: user B could receive user A's cached answer verbatim. Caught in a criticality review, fixed by putting the owner in the key. Principle: a cache key must contain every input that changes the answer — and "who is asking" became an input the moment tenancy shipped. Re-audit caches whenever scoping rules change.
The barrier that made fast agents slow The original dispatcher used asyncio.gather — every nudge waited for the slowest agent, so a 200ms activation match arrived after a 20s web search. The fix (as_completed + per-agent timeouts) required restructuring emission to be per-result — which then surfaced the next bug: the DB session opened for state loading was held across the whole 25s fan-out, pinning a pool connection per active meeting. Principles: barriers are a smell in latency-sensitive fan-outs; and never hold a pooled connection across slow I/O you don't control.
The jsonpath that wasn't a jsonpath Slicing the transcript server-side ($[last-11 to last]) failed with "function jsonb_path_query_array(jsonb, character varying) does not exist" — SQLAlchemy bound the path string as varchar; Postgres wanted the jsonpath type (cast(literal(...), JSONPATH)). Worse: the error was swallowed by a defensive except that returned None, so dispatch just… did nothing. Found live, again by outcome-asserting smoke. Principles: broad exception handlers around SQL turn errors into silence — log loudly; and exercise new SQL against a real database, not just mocks.
The binary that Redis would have mangled Packing embedding vectors as raw float32 bytes would have corrupted them — the shared Redis client runs decode_responses=True, which UTF-8-decodes everything. The cache stores base64-wrapped float32 instead (~4× smaller than JSON, text-safe), with a legacy-JSON fallback on read. Principle: know your client's decoding contract before storing non-text; migration paths beat flag-day format changes.
The ORM objects that expired mid-flight Analytics tracking committed the session — expiring loaded ORM objects — after which the endpoint touched their attributes: MissingGreenlet, the async equivalent of a lazy-load ambush. Fix: capture response values before the tracking commit; the session factory also runs expire_on_commit=False. Principle: in async SQLAlchemy there is no implicit lazy anything — read what you need, then commit.
The regex that couldn't see money The fact-check gate's \b(\$\s*\d|…) never matched "$99" — a word boundary can't exist between a space and "$" (both non-word). Nobody noticed until the eval harness's golden dataset scored the gate at 0.73 recall on day one and the failure IDs pointed straight at it. Principles: regex word boundaries only work adjacent to word characters; and untested heuristics rot invisibly — golden datasets make them visible.
The 409 that punished failure twice Upload dedupe rejected any duplicate content hash — including documents whose previous processing had failed. Users couldn't retry the exact file that needed retrying. Fix: a failed duplicate deletes the dead rows and reprocesses. Principle: dedupe on (content, outcome), not content alone — idempotency must account for failure states.
The agent rebuilt on every request The enhanced query path constructed its voice agent per request — paying initialization every call and silently wiping its in-memory conversation contexts, so multi-turn continuity never worked. Same class of bug, cold path: the doc-processing job rebuilt Docling/OCR models per document. Both became lazy singletons. Principle: any object that is expensive to build or holds session state must have an owner with a lifetime — "constructed where used" is not a lifecycle.
