Donna — Flow & Architecture

Donna is an AI meeting partner who's always a step ahead — inspired by the one from Suits. Documents become a queryable knowledge graph, pre-meeting research is auto-generated, real-time agents surface proactive nudges during the meeting, and a structured summary is delivered after. This document walks every feature, every API, every fallback. (She already knew.)

Overview

Three temporal phases, fifteen specialized agents, one continuous data flow. Each phase enriches the data model the next phase consumes.

Multi-modal documents

Docling for layout, pdfplumber for tables, EasyOCR for charts, GPT-4o-mini to normalize. All become searchable.

Real knowledge graph

Neo4j with Cypher traversal. Entities deduped via MERGE. Multi-hop paths drive in-meeting nudges.

Five parallel meeting agents

Scribe, Context, Insight, Fact-check, KG-traversal. Run via asyncio.gather after each utterance.

Real voice pipeline

LiveKit WebRTC, Deepgram streaming STT, Cartesia sonic-2 TTS. Worker auto-joins meeting-<id> rooms.

Resilience first

Circuit breakers per provider, retry with backoff, structured logs, Prometheus, rate limiting. Production patterns throughout.

Live UI updates

Per-meeting WebSocket fans nudges + utterances to the React UI. 30s heartbeat is the safety net only.

Knowledge Graph — Dual-Store Design

PostgreSQL is the system of record (foreign-key integrity to documents/chunks). Neo4j is the query layer — multi-hop traversal during meetings happens in Cypher, not in in-memory NetworkX. Entity dedup is automatic via MERGE (e:Entity {normalized, type}).

PERSON ORG ORG (focus) DATE / direct edges
Sample knowledge graph extracted from a vendor evaluation document. Amber edges animate to show kg_query_agent path traversal.
Auto-dedup via MERGE

5 spaCy hits of "Acme" across 5 chunks collapse into one node. No separate dedup pass.

Cypher path queries

1-hop and 2-hop neighbor lookups in milliseconds. NetworkX-in-memory wouldn't scale past 10k edges.

Dual-write complexity

Two writes per relationship. Mitigated by best-effort mirror — Neo4j failures don't fail the upload.

Eventual consistency

If Neo4j sync silently fails, PostgreSQL still has the edges — endpoint falls back automatically.

Fallback Strategy

The GET /documents/{id}/knowledge-graph endpoint tries Neo4j first. On miss or unavailability, it reads from PostgreSQL entities + entity_relationships tables. The response includes "source": "neo4j" | "postgresql" so the UI can show provenance.

3. DURING — Live Meeting

The centerpiece. Two input modes — manual text utterances OR real audio via LiveKit — fan into one backend endpoint, which dispatches five agents in parallel and pushes nudges over a meeting-scoped WebSocket. The bot can also speak back via Cartesia TTS.

A. Text Chat Flow (manual utterance input)

The simpler, demo-reliable path. The user types into the speaker dropdown + text box in the live meeting room. Same backend pipeline as voice — only the input source differs.

User API Persistence WebSocket Background task
Text chat flow. The API returns in < 50ms — agent fan-out runs as a background task so the UI never blocks.

B. Voice Chat Flow (LiveKit + Deepgram + Cartesia)

The full real-time path. The browser publishes a mic track to a LiveKit room named meeting-<id>. A separate Python worker auto-joins that room, streams every participant's audio to Deepgram, and POSTs final utterances to the same endpoint manual input uses.

Browser / API API call LiveKit (WebRTC) Worker / Deepgram Continuation
Voice flow. The voice worker has its own reconnect loop for Deepgram drops and retries POSTs with exponential backoff.

Worker Resilience

Deepgram reconnect: outer while True: loop wraps the WS lifecycle. Drops trigger reconnect with backoff (1s → 15s cap). The in-flight audio frame at the moment of disconnect is buffered and re-sent on the next successful connect — no lost speech.

POST retry: 5 attempts at 0.5s → 8s exponential backoff. Retries on connection errors + 5xx, gives up on 4xx (those need config fixes, not retries).

Why a separate process?

The voice worker runs outside FastAPI as its own Python process. That's the production pattern: an event loop dedicated to audio I/O, unaffected by API request latency or process restarts. It connects to the LiveKit cluster, not to the API.

C. The Five Meeting Agents (parallel fan-out)

After every utterance, agent_dispatcher.dispatch() fans out via asyncio.gather(return_exceptions=True). One agent's failure does not block the batch. Each agent returns either a nudge dict or None.

Agent Execution Model

Every agent in the system follows the same contract: async def analyze(...) -> Optional[dict]. That uniformity is what lets the dispatcher fan five of them out in parallel without bespoke wiring.

The Agent Contract

# Each meeting-phase agent
class SomeAgent:
    async def analyze(
        self,
        recent_utterances: List[Dict[str, Any]],
    ) -> Optional[Dict[str, Any]]:
        # 1. Cheap pre-check (regex / length / settings flag)
        if not _gate(recent_utterances):
            return None

        # 2. Optional LLM / external call (resilient_call wrapper)
        result = await self._llm_or_external(...)

        # 3. Return canonical nudge dict OR None
        return {
            "nudge_type": "context",
            "title": ...,
            "content": ...,
            "source_agent": "context_agent",
            "source_data": { ... },
            "relevance_score": 0.78,
        }

The Dispatcher

async def dispatch(self, meeting_id: str) -> None:
    async with AsyncSessionLocal() as session:
        meeting = await meeting_service.get_meeting(session, mid)
        utterances = meeting.transcript.utterances
        topics    = meeting.research_brief.topics

        # Fan-out — return_exceptions so one failure doesn't kill the batch
        results = await asyncio.gather(
            scribe_agent.analyze(utterances),
            context_agent.analyze(utterances),
            insight_agent.analyze(utterances, topics),
            fact_check_agent.analyze(utterances),
            kg_query_agent.analyze(meeting_id, utterances),
            return_exceptions=True,
        )

        # Persist + broadcast every non-None, non-exception nudge
        for r in results:
            if not r or isinstance(r, Exception):
                continue
            persisted = await meeting_service.add_nudge(session, mid, **r)
            await meeting_hub.broadcast(meeting_id, {
                "type": "nudge_created", "nudge": persisted.to_dict()
            })
Test coverage: the dispatcher is end-to-end-tested with all five agents mocked — see tests/integration/test_meeting_dispatch_flow.py. 83 tests pass across unit + integration.

Production Patterns

Things you'd expect at staff level — they're here, not hand-waved.

Resilient external calls

Every OpenAI / Exa / Deepgram / Postmark call goes through @resilient_call(provider) — combines tenacity retry, per-provider circuit breaker, timeout, and Prometheus counter / histogram. Per-provider state means a Deepgram outage doesn't trip Postmark's breaker.

Dependency injection

One ServiceContainer built in the FastAPI lifespan, injected via request.app.state.services. Tests swap services trivially — no globals, no monkey-patching.

Structured logging

structlog with request-ID propagation; every external call logs provider, duration_ms, success. JSON in production, console in dev. /metrics exposes Prometheus.

Rate limiting

slowapi backed by Redis. Configured per-endpoint via @limiter.limit(settings.rate_limit_upload). Disabled cleanly in tests.

Async-first end-to-end

SQLAlchemy 2.0 async + asyncpg + AsyncSession. No sync DB calls anywhere. asyncio.gather for parallel fan-outs. AsyncClient for HTTP.

Cooldowns & spam guards

Fact-check has a SHA1-hashed claim cache + 45s global throttle. KG-query has a per-(src,tgt) 90s cooldown. Cheap regex pre-checks gate every LLM call.

High-Level Design

Donna is a stateless API tier in front of a five-store data layer, with voice and heavy processing pushed to separate worker processes. Every component is chosen so the request path stays non-blocking and any single datastore can fail without taking the product down.

Stateless edge

FastAPI workers hold no session state — every request is self-describing (JWT + tenant). Scale = add replicas behind a load balancer.

Polyglot persistence

Each store does one job well: Postgres = truth, Qdrant = vectors, Neo4j = graph, Redis = coordination, MinIO/S3 = blobs.

Work off the request path

Document processing, research, summaries and voice all run async (BackgroundTasks → Arq queue). The API answers in milliseconds and the UI polls / streams.

Low-Level Design — Subsystem Internals

The four subsystems that carry the most engineering weight, drawn out in detail: how retrieval actually ranks, how a chunk becomes a contextual vector, where the voice milliseconds go, and how a nudge reaches every browser.

1 · Retrieval Pipeline (hybrid contextual RAG)

Naive dense RAG embeds the raw chunk and does cosine top-k. Donna's ContextAgent runs hybrid retrieval: contextual dense vectors fused with lexical BM25 via Reciprocal Rank Fusion, then element-aware re-ranking. The benchmark (tests/benchmarks/retrieval_eval.py) measures this against naive dense as the baseline.

Measured on the internal eval set: contextual+hybrid beats naive dense RAG by ~+9% mean across metrics, +15.8% Recall@1, +20% nDCG@1. Dense contextual embeddings alone regress (chunk homogenisation) — the lift comes from fusing with BM25.
Why two stages. ANN (HNSW) gives sub-linear recall over millions of vectors but is approximate and embedding-bound; BM25 nails exact tokens (names, numbers, IDs) the embedder smooths over. RRF needs no score calibration between them — it fuses by rank, so a strong hit in either arm survives.

2 · Three-Level Contextual Embeddings

A chunk embedded in isolation loses the meaning its neighbours and document give it. Before embedding, each chunk is enriched with three weighted context bands, mirroring Anthropic's contextual-retrieval idea — local context dominates because it's distinct per chunk; document/global are lighter to avoid homogenising every chunk in a file.

Each Qdrant point carries a tenant-scoped payload, so retrieval filters by owner_id before scoring — multi-tenant isolation at the index level, not just the app.

3 · Voice Pipeline Latency Budget

The "sub-200 ms perceived" target is a budget across the turn. The trick is overlap: partial STT transcripts stream while the user is still talking, and TTS synthesis starts before the full answer is generated. Each stage is instrumented as a Prometheus histogram so the budget is measured, not assumed.

Targets in config: STT 100 ms · TTS 80 ms · total 200 ms. Exported via observe_voice_latency(stage, ms); the 200 ms target sits on a histogram bucket edge so a single PromQL quantile answers "are we under budget?".

4 · Per-Meeting WebSocket Fan-out

Nudges must reach every participant's browser, but with N stateless API replicas the WebSocket for a meeting may live on a different replica than the one that generated the nudge. Redis pub/sub bridges them: the publisher fans out to a channel, every replica subscribed for that meeting pushes to its local sockets.

MeetingHub keeps a local socket set per meeting and bridges replicas over Redis. A nudge generated on replica A reaches a browser connected to replica B. Falls back to in-process fan-out if Redis pub/sub is unavailable; the client also polls as a safety net.

5 · Data Model — who owns what

PostgreSQL is the system of record; Qdrant and Neo4j are derived indexes kept in sync on the write path. Every tenant-scoped row carries owner_id for row-level isolation.

Scaling — Many Concurrent Sessions & 1M Documents

The POC runs single-replica on a laptop. This is the honest map of where it breaks first, and the architecture changes — not hand-waving — to take it to thousands of concurrent meetings and a million-document corpus.

Bottleneck Map — what saturates, in order

#Saturates firstSymptomFix
1In-process BackgroundTasksA restart/deploy kills in-flight ingestion; CPU-bound parsing blocks the workerMove all heavy work to the Arq queue (already built, flip USE_JOB_QUEUE) + dedicated worker fleet
2Postgres connection pool429-like stalls under concurrency; pool exhaustion (10–20 conns)PgBouncer (transaction pooling) + read replicas for the read-heavy meeting tree
3Per-utterance agent fan-out5 LLM calls × every utterance × every meeting → token spend + provider rate limitsDebounce/batch utterances, cache research, tier models, cap concurrency per tenant
4Single Qdrant nodeMemory-bound as vectors grow; tail latency on ANNQuantization + sharding + replicas (below)
5Voice worker countOne process per active room; provider concurrency capsAutoscaled worker pool on active-room metric; multi-node LiveKit
6Single LiveKit nodeSFU bandwidth / CPU on many roomsLiveKit cluster (multi-node + Redis) behind a region LB
Already done, which is why this scales cleanly: stateless API, tenant-scoped rows + vector payloads, Redis pub/sub fan-out (replica-independent), circuit breakers + retries on every provider call, and Prometheus instrumentation to see the bottleneck before guessing.

Scaling Concurrent Meeting Sessions

The text/nudge path is already horizontal (stateless API + Redis fan-out). The constraints are the voice worker pool, LiveKit capacity, and LLM concurrency. The shape: stateless front, autoscaled worker fleet keyed on active rooms, providers behind a concurrency-limited, circuit-broken client.

Scale knobs: API replicas (HPA on CPU/RPS), voice workers (autoscale on active-room gauge), LiveKit nodes (SFU capacity), and a shared, concurrency-limited provider client so a token-rate spike degrades gracefully instead of cascading.

Scaling to 1,000,000 Documents

A million documents at ~30 chunks each is ~30M vectors. The work is (a) ingesting them economically and (b) serving low-latency retrieval over them per-tenant.

Storage math (1536-d)

float32 raw~6 KB/vec → ~180 GB
+ HNSW graph~×1.4 → ~250 GB
int8 scalar quant~1.5 KB/vec → ~45 GB
binary quant + rescore~0.2 KB/vec → ~6 GB

Quantization turns "needs a huge box" into "fits across a few commodity shards with rescoring for accuracy."

Ingestion math

Embeddings30M chunks (batched)
One-time backfill~hours on a parallel Arq fleet
Embedding cost~6B tokens × $0.13/1M ≈ ~$800 one-time
Steady statequeue-driven, idempotent, resumable

Ingestion is embarrassingly parallel: shard the doc set across workers, checkpoint per-doc, retry failures.

Tenant-aware routing + sharded HNSW + quantized stage-1 recall, then exact rescore on the small candidate set. Most tenants touch one shard; the payload owner_id filter (already in the index) keeps the search space small and isolated.

Shard by tenant

Co-locate a tenant's vectors so a query hits one (or few) shards. Big tenants get dedicated shards; the long tail shares.

Hot / cold tiering

Recent / active docs in RAM-backed shards; archival corpora on disk-backed or on-demand shards. Most queries hit hot.

Postgres partitioning

Partition chunks/meetings by tenant or time; read replicas for the read-heavy meeting tree; PgBouncer for pool fan-in.

Architecture Evolution

Same code, three deployment postures. Nothing here is a rewrite — it's flipping flags, adding replicas, and sharding the stateful tier.

The POC was built stateless-first precisely so Stage 2 is a config change, not a re-architecture. Stage 3 shards the stateful tier and goes multi-region for latency + residency.

The gap between "demo" and "GA"

Already production-shaped

Stateless API · JWT auth (Argon2) · row-level multi-tenancy · circuit breakers + retries + timeouts on every provider call · Prometheus/OTel/structlog · rate limiting · Alembic migrations · 125 passing tests + retrieval & latency benchmarks.

Must close for GA

Durable job queue on by default · provider cost controls + tiering · LLM output evals & guardrails (hallucination, prompt-injection from documents) · SSO/RBAC · SOC 2 + data-residency · blue-green deploys + feature flags · per-tenant observability & quotas · backup/restore + re-index runbooks.

Cost — the real scaling constraint

At scale the bill is LLM tokens, not servers. The levers, in order of impact:

LeverWhatImpact
Model tieringCheap models for extraction/classification/nudge triage; GPT-4 only for final synthesisLargest — most calls don't need a frontier model
Prompt cachingCache the static system/persona + document context prefixesHigh on repeated-context agent calls
Embedding reuseContent-hash dedup; never re-embed unchanged chunksHigh on re-ingest / versioned docs
Batch + asyncBatch embeddings; debounce per-utterance fan-outCuts request overhead & rate-limit pressure
Per-tenant budgetsQuotas + backpressure so one tenant can't blow the billProtects margin & fairness
The honest one-liner. The POC proves the product and the architecture is deliberately stateless + tenant-isolated + instrumented so scaling is additive, not a rewrite. The path to market is durability, cost controls, evals, and compliance — engineering that's well-understood, not invention.
