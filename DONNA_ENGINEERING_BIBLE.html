What Donna Is & How To Read This

Donna is an AI meeting collaborator. Not a transcription tool that summarizes after the fact — a participant that prepares before the meeting, listens and contributes during it, and remembers after it. The product covers the full meeting lifecycle:

🔭 BEFORE

Describe the meeting in plain language → Donna structures it (goal, agenda, risks), researches the topics on the live web with source-credibility tiers, emails pre-reads and invites, and imports your calendar so meetings arrive pre-briefed.

🎙 DURING

Every spoken sentence fans out to nine live agents. Donna detects decisions, checks factual claims against the web, pulls relevant documents and past-meeting memories, tracks the agenda, watches talk-time balance — and pushes each insight as a card the moment it's ready. She can even speak high-signal nudges aloud.

🧠 AFTER

A structured summary with decisions (and the verbatim quotes that triggered them), persisted action items with lifecycle tracking, calendar exports, per-assignee follow-up emails — and everything is indexed into memory so future meetings recall "in March you decided…".

Questions this section answers What problem does Donna solve? Why is it architected as three phases?

The founding insight: meetings fail from misalignment — people arrive unprepared, decisions evaporate, and knowledge dies in transcripts nobody reads. Each phase attacks one of those failure modes, and each phase has fundamentally different latency and cost characteristics — which is exactly why the architecture splits into hot, warm and cold paths (Section 02).

Donna is a modular monolith + workers: one FastAPI backend holding the domain logic, three worker processes for everything latency-tolerant or long-running, five data/infra services, and a Next.js frontend. Twelve containers total, one docker compose up.

Why a modular monolith instead of microservices? A meeting product's domain objects (meeting, transcript, nudge, decision) are deeply interrelated — splitting them into services would turn in-process function calls into network calls with distributed-transaction problems, for zero scaling benefit at this stage. The things that genuinely need process isolation are isolated: CPU-heavy document OCR (job-worker), audio streaming (voice-worker), and the conversational agent (assistant-worker) each run separately so they can never starve the API's event loop. The seams for a future split already exist — they're the router/service boundaries.
Q: Why do the workers import from apps/api? Deliberate. Workers reuse the same service layer, models, and config as the API — one source of truth for business logic. The cost is that worker images contain the whole app; the benefit is that a bugfix in, say, the summary pipeline applies everywhere with no version skew.

Architectural Drivers — How To Settle Any Argument

Most architecture disagreements are not disagreements about facts. They are two people optimizing different quality attributes, and neither one saying which. A stated, ordered list of drivers converts an argument about taste into a lookup. This is Donna's list, and the order is the whole content.

The order

1
Tenant isolation. No path may return one owner's knowledge to another. Beats everything, including availability and latency. A system that refuses to answer is recoverable; a system that answered with someone else's board deck is not.
2
Provenance. Every assertion Donna makes in a room full of people carries its source. An uncited claim mid-meeting is not a feature with a caveat — it is the product actively doing harm, because people act on it.
3
The meeting never stalls. Transcription, and the human experience of the meeting, must survive every downstream failure. Intelligence is an enhancement layered on a spine that does not depend on it.
4
Time-to-first-insight. A nudge that arrives after the topic has moved on is worth zero — not "less." This is why the fan-out streams instead of gathering, and why timeouts are per-agent.
5
Cost per meeting-hour. The economic thesis. Nine agents per spoken sentence is only viable if the typical sentence costs nothing, which is what the deterministic gates buy.
6
Operational simplicity. Every stateful component is a new backup story and a new page at 3am. Neo4j earns its place only by being optional in code.
7
Ingestion throughput. Deliberately last. Document processing is asynchronous, amortized and retryable; nobody is watching a spinner.

Watching the order do real work

Four decisions in this codebase are only explicable by that ordering. Each one looks wrong if you rank the drivers differently:

Access failures return 404, not 4031 > usability

Requesting a meeting you don't own returns "not found" — a worse error message, and genuinely more confusing to debug.

Driver 1 beats developer convenience. A 403 confirms the resource exists. Enumerating IDs against a 403/404 split is a membership oracle: it leaks who is meeting with whom, which for a meeting product is close to the whole secret.

The RAG cache key contains the owner1 > 5

Adding owner_id to the key lowers the hit rate — the same question asked by ten people is now ten cache misses and ten paid answers.

Driver 1 beats driver 5. Retrieval is tenant-scoped, so the same question has different correct answers per user. An owner-less key isn't a cheaper cache; it's a cross-tenant leak that happens to be fast (§30).

Metering is best-effort and swallows everything3 > 5

llm_meter.record() wraps its whole body in except Exception: pass. Cost data can be silently lost.

Driver 3 beats driver 5. Losing a cost datapoint costs a rounding error on a dashboard. Letting the meter raise into a live agent call costs the nudge — and the accounting layer must never be able to break the thing it accounts for.

Agents run on finals, never interims5 > 4

Interim STT results arrive continuously and would let agents start reasoning ~1–2s earlier.

Driver 5 beats a marginal driver 4. Interims re-transcribe the same words as confidence improves; running nine agents per revision multiplies cost roughly tenfold for no insight gain. Interims still serve latency feel as ghost text — the cheap half of the benefit, kept.

Why publish the order at all? Because the alternative is re-deriving it, badly, in every code review. When someone proposes caching RAG answers globally "for the hit rate," the review is no longer a debate about caching — it's a lookup that says driver 1 outranks driver 5, and the proposal is closed in one sentence. Ordered drivers are the cheapest governance a codebase can have.

The Invariants — A Constitution

Drivers are how you rank competing goods. Invariants are different: they are the statements that must be true after every commit, and a change that breaks one is a bug even if every test passes and the product feels better. There are nine.

1
Every stored vector carries its owner_id in its payload, and every search filters on it. Isolation lives in the index, not in the endpoint — so it cannot be bypassed by a clever query path or a new caller who forgot.
2
Every cache key contains every input that changes the answer. Including "who is asking," which became an input the day tenancy shipped. Whenever scoping rules change, all cache keys are re-audited.
3
Provenance is written at index time, never reconstructed at read time. A chunk knows its filename, section and page; a memory knows its meeting, date and verbatim quote. Every surface — nudges, assistant, MCP — cites from the same stored fields.
4
No agent may block another. Every agent has its own timeout and its own emit; failures degrade to None. A cycle produces the results that were ready, never "all or nothing."
5
A pooled DB connection is never held across I/O the process does not control. State loads in one short session; each emit opens its own. Nothing stays checked out across a 25-second web search.
6
Absent configuration is a first-class state, not a crash. No Google credentials → the endpoint 503s and the button hides. No Redis → locks no-op, hub goes in-process, queue falls back. Degrade, announce, continue.
7
The transcript is append-only and row-locked. Concurrent speakers cannot lose words. This is the one place the system takes a real lock, and it is per-meeting, so it shards naturally.
8
Re-indexing is idempotent. Deterministic UUIDv5 point IDs mean re-processing a document overwrites rather than duplicates — which is what makes "improve the pipeline and re-run everything" a safe operation instead of a migration project.
10
A customer's database is read-only, scoped, and audited. Donna issues only SELECTs, only against tables the customer explicitly approved, only through a session the server has forced read-only — and every statement is logged where the customer can read it. No code path may reach a customer database except through services/data_connection/service.py, because that is where the audit is written (§11).
9
Schema is owned by Alembic, never by the application. The app assumes schema; it does not create it. CI applies the full chain to a fresh Postgres and then runs alembic check for model drift.
Invariant 4 is the one that gets broken by accident It is extremely natural to write results = await asyncio.gather(*agents) and then loop over the results. That code is correct, readable, and quietly destroys the product's core latency property — a 200 ms activation match arrives 20 seconds late because a web search was in the same batch. This exact regression already happened once (§30). If you touch agent_dispatcher.py, the streaming shape is load-bearing.

What this design explicitly does not support

Naming non-goals is not modesty; it is how you stop a roadmap from being negotiated one exception at a time. Each of these is a deliberate "no," not an oversight:

  • Real-time document ingestion. Upload → queryable is seconds to minutes of OCR, layout analysis and embedding. There is no "attach this PDF and ask about it in the same breath" — attach it before the meeting.
  • Speaker identification from audio alone. Attribution comes from LiveKit track identity. The conference-room case (one shared mic) falls back to acoustic diarization labelled "Name — Speaker N", which is deliberately approximate.
  • Editing the transcript. It is append-only. Correcting a mis-transcription would invalidate the decision quotes and memory records derived from it, and there is no re-derivation path.
  • Cross-tenant knowledge. Two users at the same company have two disjoint knowledge bases. Team-shared corpora need an ownership model (org_id alongside owner_id) that does not exist yet, and it needs a design before it needs code.
  • Contradiction resolution. When a document and a web source disagree, both surface with their confidence and tier. For a product whose job is to prevent errors, silently picking a winner is the wrong behaviour — but showing both is a punt, not an answer.
  • Retroactive re-analysis. Improving an agent does not re-run it over past meetings. Nudges are events, not derived views.
  • Languages other than English. Deepgram is pinned to en-US, the stopword lists are English, and spaCy loads an English model. Nothing is architecturally English-only; nothing has been tested otherwise.

Q: Four datastores — isn't that over-engineering? Each store holds a different shape of the same knowledge, chosen by query pattern: rows you filter and join (Postgres), vectors you rank by similarity (Qdrant), edges you traverse (Neo4j), blobs you fetch whole (MinIO), plus Redis for everything ephemeral. Forcing one store to do all five jobs is how you get 500ms queries and un-debuggable data. The teaching point: pick stores by access pattern, not by fashion — and make the optional ones (Neo4j) actually optional in code.

The load-bearing bets, in full

Four choices define this system. If any one of them is wrong, the architecture is wrong — so each gets the full treatment, including the condition that would retire it.

Redis as five things at oncethe highest-leverage bet

One Redis instance serves as: the cache (embeddings + RAG responses), the distributed lock manager (one dispatch cycle per meeting), the pub/sub bus (WS fan-out across replicas + the TTS speak channel), the job queue (Arq), and the counter store (cost meter, cooldowns, learned-mute). Five architectural roles, one dependency.

Why
Each role individually would justify a lighter-weight tool, and collectively they would justify four. But every one of the five is ephemeral, low-durability, high-frequency state — the exact shape Redis is built for. Consolidating them means one connection pool, one health check, one failure mode to reason about.
Beat
Celery + RabbitMQ for jobs (a broker with a sync worldview and its own operational surface), Postgres advisory locks (couples the hot path to the transactional DB), an in-process asyncio.Lock (correct on one replica, silently wrong on two), and Memcached for caching (no pub/sub, no Lua, no data structures).
Trade-off
One blast radius. A Redis outage touches five subsystems at once. This is only acceptable because every one of the five degrades rather than fails: locks no-op to process-local, the hub delivers in-process, the queue falls back to BackgroundTasks, caches miss, and the meter drops writes. That is not a happy accident — it is written into each call site as an except path, and it is invariant 6.
Revisit when
(a) Job-queue throughput starts competing with pub/sub for the same event loop — split the queue onto its own instance first, not onto a new technology. (b) Cache working set exceeds what you want in the same memory budget as the lock keyspace. (c) You need job priorities or per-tenant fairness, which Arq does not model — that is the point at which the queue, specifically, outgrows this choice.
Postgres computes over JSONB rather than shipping itwhy not a document DB

Transcripts are a JSONB array on one row per meeting. The naive reading of that design is "they should have used MongoDB." The reason they did not is that the hot path never reads the array — it reads a server-side slice of it:

apps/api/services/meeting/meeting_service.py — get_dispatch_state()the reason JSONB works here
# Only the recent window leaves Postgres — agents look at the last few # utterances, and shipping a 2-hour meeting's full JSON array on every # dispatch cycle scales with meeting length. select( func.jsonb_path_query_array( cast(MeetingTranscript.utterances, JSONB), cast(literal("$[last-11 to last]"), JSONPATH), ), func.jsonb_array_length(cast(MeetingTranscript.utterances, JSONB)), ).where(MeetingTranscript.meeting_id == meeting_id)
Why
A 2-hour meeting is ~2,000 utterances. Agents need the last 12. Slicing in Postgres means each dispatch transfers a bounded payload regardless of meeting length — the cycle cost is O(1) in meeting duration, not O(n). The same trick powers the flow agent, which aggregates per-speaker word counts with jsonb_array_elements in one query rather than counting in Python.
Beat
MongoDB (would ship the whole document, and gives up the transactional joins that decisions/action-items need), a separate utterances table (a row per utterance is the "correct" normalization — and costs an INSERT plus index maintenance per spoken sentence, plus an ORDER BY LIMIT on every read, for data that is only ever appended and read as a window).
Trade-off
Appends need SELECT … FOR UPDATE on the transcript row, so concurrent speakers serialize through one lock. That lock is per-meeting, so it shards naturally — but it does mean a single meeting has a write ceiling. At conversational speech rates this is nowhere near binding.
Revisit when
You need to query across utterances globally ("every time anyone said 'budget' in any meeting"). That is a search problem over rows, and it is the point at which utterances want to be their own table — or, more likely, their own index in the vector store, which is where meeting memories already live.
The bug this design already caused $[last-11 to last] failed in production with "function jsonb_path_query_array(jsonb, character varying) does not exist" — SQLAlchemy bound the path as varchar, Postgres wanted the jsonpath type. The explicit cast(literal(...), JSONPATH) above is the fix. Worse than the bug: a defensive except swallowed the error and returned None, so dispatch silently did nothing. Full story in §30.
Neo4j, but optional in codeoperational simplicity vs capability
Why
Two agents genuinely need graph traversal: kg_query ("vendor X appears in your Q3 contract and the security audit" — a 1–2 hop path) and memory (the Meeting→Decision→Topic subgraph). Both are multi-hop questions whose SQL form is a recursive CTE that nobody wants to maintain.
Beat
Recursive CTEs in Postgres (fewer moving parts, materially worse ergonomics for path queries), and doing without connection-finding entirely (which removes one of the two features that make Donna feel like it knows things rather than searches things).
Trade-off
A fifth datastore, violating driver 6. The trade is bought back by a hard rule: Neo4j is never a dependency, only an enhancer. Embeddings, Retrieval & RAG — The Honest Version

This section teaches retrieval the way the codebase learned it — including the negative result most tutorials skip: contextual embeddings alone did not beat naive RAG. The measured win comes from fusing them with lexical search.

What "3-level contextual embeddings" actually means

A chunk's raw text often can't answer "what is this about?" on its own — "revenue grew 15%" means nothing without knowing it's from the Q3 board deck, section Financials. So each chunk is embedded three times, with three different context windows folded in (apps/api/services/document/contextual_processor.py):

LevelWeightContext folded into the embedded textWhat it's good at
Local50%The surrounding chunks (previous/next window)Precise passage-level matches
Document30%Document title + section path"In the vendor contract, what…" queries
Global20%Genuinely related other documents, found by a tenant-scoped Qdrant probe at ingestion timeCross-document connections

The three vectors are stored in three Qdrant collections (_local, _document, _global), and their average goes into _unified. Query time can search one level or fuse all of them with those weights.

The honest finding (measured, not vibed) The retrieval suite runs three arms over a ground-truth corpus: naive dense RAG, contextual-dense, and contextual + BM25 hybrid. Result: contextual embeddings alone under-perform naive dense retrieval — folding shared context into every chunk homogenizes chunks within a document, so the thing that helps you find the right document hurts you when picking the right passage inside it. The hybrid, which fuses the contextual dense ranking with lexical BM25 via Reciprocal Rank Fusion, is what wins. Lesson: measure your retrieval; the fancy technique is not automatically the better one — and name the pipeline after what it does, not after the technique you hoped would carry it.

The committed floors, exactly as they sit in the repo

These are the values CI enforces. They are floors, not the last measurement — the harness ratchets them upward via --update-baselines when a change is a genuine improvement, so the gap between a floor and the current run is deliberate headroom, not slack:

Gating mrr_lift_vs_naive means the day the fancy pipeline stops earning its complexity, the build goes red and tells you to delete code. Very few systems instrument their own obsolescence; this is what it looks like.

Query-time flow. The same retrieval core serves the API, the in-meeting context agent, the assistant panel, and the MCP server.

The Caching Layers, Each Justified

Caching looks like an optimization chapter. It is actually a correctness chapter: two of the three caches here have a tenancy property in their key, and the one time that was got wrong it was a cross-tenant data leak rather than a performance bug. Cache keys are a security surface.

CacheTTLKeyWhy it exists, and why that TTL
Embedding cache 24 h emb:q: + sha256(model:text)[:24] Embeddings are deterministic for a given model + text, so they can live far longer than anything derived from documents. Repeats are constant — burst dispatches re-embed the same rolling window, common questions recur, the context agent re-queries every cycle. The model is in the key because a model swap must invalidate everything without a flush.
RAG response cache 5 min rag:query: + sha256(owner:query:level)[:16] Short, because answers go stale the moment documents change. The owner is in the key because retrieval is tenant-scoped — the same question has different correct answers per user. Explicitly invalidated on upload/delete rather than relying on the TTL, because a five-minute window of stale answers after an upload is exactly when someone is testing whether the upload worked.
In-process embedding memo process life hash(text), FIFO capped at 256 Saves even the Redis round-trip within a single burst. Capped, because an unbounded dict in a long-running API process is a memory leak with a slow fuse — the kind that looks fine in staging and pages you in week three.

The key function, and the comment that is load-bearing

apps/api/core/cache.pythe owner_id line is a security control
def _cache_key( query: str, context_level: str = "document", owner_id: Optional[str] = None ) -> str: """Generate a deterministic cache key from owner + query + context level. ``owner_id`` MUST be part of the key: retrieval is tenant-scoped, so the same query returns different answers for different owners. """ raw = f"{owner_id or 'global'}:{query.strip().lower()}:{context_level}" return CACHE_PREFIX + hashlib.sha256(raw.encode()).hexdigest()[:16]
Read the fallback carefully owner_id or 'global' means an unauthenticated (dev-mode) caller shares one cache namespace. That is correct only while REQUIRE_AUTH=false is a dev-only setting. If a deployment ever ran with auth off and multiple real users, they would share cached answers. The mitigation is that production sets REQUIRE_AUTH=true — which is a configuration guarantee protecting a correctness property, and that is weaker than it should be. Logged in the defect register (§29).

Packing vectors: a small function with two bugs designed out of it

apps/api/core/cache.py — vector packing4× smaller, text-safe, back-compatible
def _pack_vector(vector: list) -> str: """float32 + base64: ~4x smaller than a JSON float list, and Redis is configured with decode_responses=True so values must stay text.""" return base64.b64encode(struct.pack(f"<{len(vector)}f", *vector)).decode("ascii") def _unpack_vector(raw: str) -> list: if raw.startswith("["): # legacy JSON entry from before packing return json.loads(raw) buf = base64.b64decode(raw) return list(struct.unpack(f"<{len(buf) // 4}f", buf))

Three decisions are compressed into those eight lines, and each is worth naming:

Why not raw bytes

The shared Redis client runs decode_responses=True, which UTF-8-decodes every value. Raw float32 bytes would be silently mangled — corrupt vectors, no exception. Base64 keeps it text-safe.

Why not JSON

A 1536-dim float list as JSON is roughly 4× the size of packed float32, on every read and write, for a cache that holds one entry per distinct query.

Why the "[" check

A one-line migration path. Old JSON entries keep working until they expire, so the format change needed no flush and no flag day.

The transferable rule Before storing non-text in any client, know its decoding contract — and prefer a read-side format sniff over a flag-day migration. A cache is the one place where a format change is free if you do it this way: worst case, entries miss once and repopulate.

Groundedness — the check that runs on every answer

Retrieval quality answers "did we find the right chunks?". It does not answer "does the sentence we generated actually say what those chunks say?" — and an ungrounded claim arriving with a citation attached is more credible than one without, not less. services/rag/groundedness.py closes that gap deterministically: no model call, microseconds, so it can run inline on every answer.

It targets fabricated specifics — a number, date, amount or proper noun asserted in the answer but absent from the context. That is the highest-risk and most detectable class of hallucination, and catching it well beats catching everything badly. Three refinements came directly from its own eval failures: evidential framing ("the sources confirm…") is stopworded because it is scaffolding rather than assertion; initialisms resolve against their expansions (a document saying "Master Services Agreement" licenses an answer saying "MSA"); and light suffix stemming stops a correct paraphrase scoring as unsupported purely for rewording.

What is deliberately not cached

  • Agent outputs. A nudge is a function of the conversation so far; caching it would mean replaying stale insight into a moved-on discussion. Cooldowns (per-claim, per-person, per-nudge-type) do the de-duplication job instead, and they are time-based rather than content-based on purpose.
  • Meeting state. The dispatcher re-reads state every cycle. It is a handful of targeted selects plus a bounded jsonpath slice — cheaper than any invalidation scheme that would have to be correct across replicas.
  • Research briefs. Written once, read many, and already a row. The database is the cache.

Connecting a Company Database — Read-Only, and Paranoid About It

Donna's insights are only as good as the base she reasons over. Documents supply that base when somebody remembers to upload one — and in the common case, nobody does. So a company can connect Donna to their own database, read-only, once, in Settings. From then on the agenda has something factual behind it.

Read this chapter as a security chapter, not a feature chapter Everything here reads a customer's production database. A defect is not a degraded feature — it is unauthorised access to a system Donna does not own, cannot revoke, and whose outage it cannot fix. The design bias throughout is therefore refuse rather than risk, and every control assumes the one in front of it has already failed.

Why this exists at all

An agenda item like "review vendor spend" is unanswerable from the open web. Web search describes the world; the company's own data describes their situation. Before this feature, a meeting with no attached documents gave the context agent nothing to retrieve and the research pipeline nothing but generic industry links — which is precisely the case where a proactive assistant most needs a base and least has one.

Where the data is used, and why the paths differ

The single most consequential decision here is not to query a customer's database on the hot path. The context agent has a 10-second budget and runs on every utterance; live text-to-SQL there would blow the latency budget, add an LLM call per spoken sentence, and put generated SQL against someone's production database on the critical path of a live conversation. So the paths split by latency class, exactly like everything else in §02:

HOT In-meeting Context agent, < 10s budget Indexed snapshot. The eleven guardrails

Layered deliberately: any one could be defeated by a determined bug, and the bar is that all of them fail at once. Listed outermost first.

Where we connect

1
SSRF guard. A user-supplied host is an SSRF primitive, because the server does the dialling — so the server's network position is what an attacker gets. Blocked: loopback, every RFC1918 private range, reserved/multicast, Donna's own service hostnames (postgres, qdrant, neo4j…), and critically 169.254.169.254, the link-local range holding cloud instance-metadata endpoints that hand out IAM credentials on AWS/GCP/Azure. Every resolved address is checked, so a hostname with both a public and a private A record cannot slip through on the first match.
2
TLS by default. require is the default; verify-full is offered; disable exists but is labelled "not recommended" rather than presented as a neutral third option.
3
Connection timeout. An unreachable host must never hang a worker.

What we run

4
Session forced READ ONLY at the server, plus statement_timeout and idle_in_transaction_session_timeout. If every check above were bypassed, Postgres itself would still reject a write on this session. This is the layer that does not depend on our code being correct.
5
SQL allowlist, not blocklist. The statement must start as SELECT or WITH after normalization, and must be a single statement. A blocklist alone loses to the first encoding trick nobody anticipated.
6
Forbidden functions — pg_read_file, lo_import, dblink, pg_sleep and friends: file access, network egress, and denial of service.
7
Table allowlist. Nothing is readable until the customer ticks a specific table. Unrecognised references are treated as disallowed, because a false rejection costs an insight and a false acceptance costs a read they never sanctioned.
8
Column denylist. Names matching password / token / secret / SSN / card / IBAN / DOB patterns never leave their database — enforced at planning and again on the result set.
9
Mandatory row cap, applied by wrapping the statement rather than appending LIMIT. Appending is unreliable — the statement may already have a limit, end in a comment, or use a set operation. Wrapping is unconditional, and Postgres pushes the limit down anyway.

Accountability

10

The control worth defending in a security review

Verification does not trust the instruction "use a read-only user." It proves it:

services/data_connection/connector.py — verify()trust nothing, test everything

The setup flow is three decisions, not one button

Credentials. Host is SSRF-checked before anything is persisted — a stored-but-unusable connection is worse than a clear failure. The password is encrypted on the way in and is write-only across the entire API surface: there is deliberately no code path that could return it.
Verify & discover. Donna connects, runs the write probe, and reads the catalog only — table and column names, types, row estimates. No business data is read at this stage, so a customer can see exactly what Donna learned before any of their actual rows are touched. Row counts come from pg_class.reltuples, not count(*): counting every table on a large database at setup time would be exactly the load this feature must not generate.
Approve tables. The discovered schema is shown with sensitive columns flagged, not hidden — silently omitting them would make the schema view a lie. Nothing is read until specific tables are ticked. Approving nothing is a valid, supported end state: it means "read none of my data".

The LLM is an untrusted source of SQL

Query planning uses a model, and the model is treated as a convenience for phrasing a query — never as an authority on what may execute. Two independent layers, and the second does not assume the first worked:

Layer 1 · Prompt scopingwhat it can see

The model is shown only approved tables, with sensitive columns already stripped. It cannot reference what it was never shown.

Layer 2 · Execution guardswhat may run

Everything returned is re-validated — SQL allowlist, table allowlist, row cap — before it reaches the database. A proposal that references an unapproved table is logged as a warning, because it means prompt scoping alone would not have been sufficient.

Rejected queries are discarded, never repaired There is no automatic "fix the SQL and retry" loop. An agent iterating against someone else's production database is exactly the wrong place to be clever, and a repair loop turns one bad proposal into several. A rejected query is logged with its reason and dropped.

What it costs the customer, stated plainly

  • Freshness. In-meeting facts are as current as the last sync, not live. For automatic nudges that is the right trade; explicit questions take the live path.
  • A sample, not a replica. The snapshot is capped per table. Copying a customer's entire database into a vector store would be a different product with a different consent conversation.
  • Their data lands in Donna's vector store. Owner-scoped and column-filtered, but it is a copy. That belongs in a contract, not only in a config screen.
Untested against a real external database Every guard is unit-tested adversarially (74 cases) and verified live inside the running container, but the feature has never been pointed at a genuine third-party Postgres. The guards are proven; the integration is not. Logged in §29.

The Hot Path, Line By Line

This is the heart of Donna and the most instructive piece of engineering in the codebase: a streaming multi-agent supervisor. One utterance in, up to nine insights out — each delivered the instant its agent finishes, never waiting for the slowest.

The successor to docs/diagrams/07-five-agent-fan-out.svg — nine agents, streamed. Fast free agents (green) emit in milliseconds while fact-check is still searching the web.

Walking the code

Utterance lands. routers/meetings.py → POST /{id}/utterances — accepted from a user JWT or the voice worker's service key. The append takes a row lock on the transcript (concurrent speakers can't lose words), broadcasts utterance_added, then enqueues dispatch_job.
One cycle per meeting. agent_dispatcher.dispatch() takes a Redis distributed lock with wait=False. If a cycle is already running, it sets a pending flag and returns — the running cycle re-runs once over the newer state when it finishes (max 3 coalesced cycles). Rapid speech produces one catch-up pass, not a queue of stale duplicates.
State loads slim, connection releases fast. meeting_service.get_dispatch_state() issues targeted selects: owner, attendees, agenda, started_at, decision count, research topics, attached doc ids — and the transcript via a server-side jsonpath slice ($[last-11 to last]) so a 2-hour meeting ships 12 utterances, not 2,000. The session closes before the fan-out: holding a pooled connection through a 25-second agent cycle is how you exhaust a pool at ten concurrent meetings.
Nine tasks, streamed. Each agent is wrapped in _run_agent() — tracing span + asyncio.wait_for with its own budget. Then for fut in asyncio.as_completed(tasks): each finished agent's nudge is emitted immediately. The old design (gather) made a 200ms activation nudge wait for a 20s web search — the barrier was the bug.
Emit = suppress-check → persist → speak? → broadcast → metric. Each in its own short DB session. should_suppress consults the learned-mute stats (§18); _maybe_speak_nudge publishes to the TTS channel if the leader enabled voice and relevance ≥ 0.8 (2-min cooldown); the WS payload is built from the persisted row; a nudge_created analytics event records it for the acceptance-rate metric.
The supervisor pattern, generalized If you build one thing from this document, build this: N specialist agents · each with a free pre-check · each with a timeout · results streamed, not gathered · failures degrade to None. It gives you bounded latency (slowest useful agent, not slowest agent), bounded cost (most utterances never touch an LLM), and graceful partial failure (a Neo4j outage costs you connection nudges, not the meeting). Every design choice falls out of asking: what must never block what?

The Dispatcher's Six Mechanisms

agent_dispatcher.py is 347 lines and carries the entire live product. This chapter takes it apart mechanism by mechanism, with the actual code, because each one is a pattern that transfers to any multi-agent system — and because the file is small enough that every line can be justified.

Mechanism 1 · Timeouts as a declared policy, not scattered constants

The timeouts live in one dict at module scope, ordered and commented with why each agent gets its budget. That placement is deliberate: a reviewer can audit the entire latency policy of the product in nine lines, and changing one is a visible diff rather than an argument buried 200 lines into a function.

apps/api/services/meeting/agent_dispatcher.pythe whole latency policy, in one place
# Per-agent wall-clock budgets (seconds). Tiered by dependency class: # in-process matchers < retrieval < LLM/web calls. _AGENT_TIMEOUTS = { "scribe": 12.0, # regex pre-check + one gpt-4o-mini call "context": 10.0, # embedding + Qdrant "insight": 12.0, # gpt-4o-mini topical match "fact_check": 25.0, # Exa search + verdict call "kg_query": 8.0, # spaCy + Neo4j traversal "activation": 2.0, # pure token matcher "memory": 6.0, # Neo4j decision recall "agenda": 3.0, # pure lexical matcher + one UPDATE on transitions "flow": 5.0, # one SQL aggregate every Nth utterance }
Why the budgets are tiered by dependency class A timeout is a statement about what you expect the work to touch. A pure in-process matcher that needs more than 2 seconds is broken, not slow — so a tight budget converts a logic bug into a visible timeout warning instead of a mysteriously sluggish cycle. Conversely fact-check gets 25 s because it makes a live web round-trip, and cutting it shorter would turn a working feature into a coin flip. Budgets should be tight enough to catch bugs and loose enough to permit the real work — which means they must differ per agent.

Mechanism 2 · Failure isolation at the wrapper

Every agent goes through one wrapper that does three things: opens a tracing span, applies the budget, and converts any failure into None. Invariant 4 lives in these fifteen lines.

agent_dispatcher.py — _run_agent()one agent's bad day never becomes the cycle's
async def _run_agent(name: str, coro) -> tuple[str, Optional[Dict[str, Any]]]: """Run one agent with tracing + timeout; failures degrade to None.""" timeout = _AGENT_TIMEOUTS.get(name, 15.0) try: if settings.enable_tracing: tracer = get_tracer("meeting.agents") if tracer is not None: with tracer.start_as_current_span(f"agent.{name}"): return name, await asyncio.wait_for(coro, timeout) return name, await asyncio.wait_for(coro, timeout) except asyncio.TimeoutError: logger.warning(f"[Dispatcher] agent '{name}' timed out after {timeout}s") return name, None except Exception as e: logger.warning(f"[Dispatcher] agent '{name}' error: {e}") return name, None
Note what it returns, not just what it catches It returns (name, None) — the name survives the failure. That is what lets the caller distinguish "agent ran and had nothing to say" from "agent died," and it is why the timeout log line can name the culprit. A bare None would have made every failure anonymous. When you swallow an error, keep the identity.

Mechanism 3 · Burst coalescing instead of a queue

People speak in bursts. Three utterances in four seconds must not produce three full nine-agent cycles over nearly identical state. The naive fixes are all worse: debouncing adds latency to the common case, and queueing produces a backlog of cycles analysing state that is already stale by the time they run.

The actual mechanism is a lock that refuses to wait, plus a pending flag:

agent_dispatcher.py — dispatch()N rapid utterances → 1 extra cycle, capped at 3
for _cycle in range(_MAX_COALESCED_CYCLES): # _MAX_COALESCED_CYCLES = 3 async with distributed_lock( f"dispatch:{meeting_id}", ttl_seconds=45.0, wait=False ) as acquired: if not acquired: # A cycle is running — ask it to go once more, then stop. await self._set_pending(meeting_id) return await self._dispatch_locked(meeting_id, mid) if not await self._consume_pending(meeting_id): return # nothing arrived while we were analyzing
Design elementWhat it prevents
wait=FalseA thundering herd of dispatchers blocked on one lock, each holding a task slot for the duration of somebody else's fan-out.
Pending flag, not a counterTen utterances during one cycle produce one catch-up pass, not ten. The flag is idempotent by construction — this is the whole trick.
_MAX_COALESCED_CYCLES = 3An unbounded loop during continuous speech. Someone talking without pause would otherwise keep re-arming the flag forever, and the cycle would never release.
ttl_seconds=45.0A crashed dispatcher holding the meeting's lock permanently. The TTL is comfortably above the 25 s worst-case fan-out, so it expires only on genuine death.
_consume_pending uses DELETEA race where two replicas both see the flag and both run a catch-up cycle — Redis DELETE returns whether it actually removed something, making the check atomic.

Mechanism 4 · The lock that degrades to a different lock

distributed_lock is Redis SET NX PX with a Lua compare-and-delete release, falling back to a process-local asyncio.Lock when Redis is unreachable. The compare-and-delete is the part people skip, and it is the part that matters:

apps/api/core/coordination.pyrelease only a lock you still own
# Compare-and-delete so we only release a lock we still own. _UNLOCK_LUA = """ if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end """
The failure this prevents Without the token comparison: cycle A overruns its 45 s TTL, the lock expires, cycle B acquires it, then A finishes and calls DEL — deleting B's lock. Now C can acquire it too, and two cycles run concurrently on the same meeting, double-emitting nudges. The Lua script makes release conditional on still holding the same token, and Lua makes that check-and-delete atomic. Any lock with a TTL needs a fenced release; a bare DEL is a correctness bug waiting for a slow day.
The fallback is honest about being weaker When Redis is down the lock becomes process-local, which serializes dispatch within one replica and not across replicas. On a multi-replica deployment that means duplicate nudges during a Redis outage — degraded, and deliberately degraded, because the alternative (refusing to dispatch at all) would take the live product down for a cache outage. Driver 3 over driver 1's strictest reading, and the only place in the system where that trade is made.

Mechanism 5 · Streaming emission, with a cancellation guard

The heart of the file. Note the finally — it is not decoration:

agent_dispatcher.py — _dispatch_locked()as_completed, not gather
created = 0 try: # Stream: each nudge reaches the room the moment its agent # finishes — fast agents are never blocked by slow ones. for fut in asyncio.as_completed(tasks): name, nudge = await fut if not nudge: continue if await should_suppress(owner_id, nudge["nudge_type"]): continue if await self._emit_nudge(mid, meeting_id, nudge): created += 1 finally: # No-op on the normal path (all done); on an exception it # stops orphaned agent tasks from running unobserved. for t in tasks: t.cancel()

If the emit path raises — a DB blip, a serialization error — the loop exits with tasks still in flight. Without the finally, those tasks keep running detached: they consume LLM budget, hold connections, and log errors nobody can attribute to a cycle that already ended. Any time you exit a loop over as_completed early, you own the remaining futures.

Mechanism 6 · One short session per emit

Invariant 5, made concrete. State loading opens a session and closes it before the fan-out starts; each emit then opens its own:

agent_dispatcher.py — session lifetimeswhy the pool survives ten concurrent meetings
# Short-lived session: load state, release the connection. # Holding one across the (up to 25s) agent fan-out would pin a # pool connection per active meeting and exhaust the pool. async with AsyncSessionLocal() as session: state = await meeting_service.get_dispatch_state(session, mid) …fan-out happens here, holding NO database connection… async def _emit_nudge(self, mid, meeting_id, nudge) -> bool: """Opens its own short-lived session so DB connections are only checked out for the milliseconds of the write, not the seconds the agents spend thinking.""" async with AsyncSessionLocal() as session: return await self._emit_nudge_in_session(session, mid, meeting_id, nudge)
Do the arithmetic — this is why it matters A default async engine pool is small. Hold one connection per active meeting across a 25 s fan-out and ten concurrent meetings exhaust it; the eleventh request blocks on checkout, the health check times out, and the symptom presents as "the API is down" with no slow query anywhere in the logs. The connection was never busy — it was held. That distinction is invisible in every dashboard, which is what makes this class of bug so expensive to diagnose after the fact.

What runs after an agent returns, in order

Suppression check. should_suppress(owner_id, nudge_type) — the learned-mute gate. Reads two Redis counters; returns False on any error so learning can never block a nudge.
Persist. meeting_service.add_nudge(...) in its own session, returning the row so the broadcast carries a real ID the frontend can pin or dismiss.
Speak? _maybe_speak_nudge — three gates in sequence: the type is in {fact_check, decision_prompt}, relevance ≥ 0.8, and the leader has enabled voice. Then a SET NX EX 120 cooldown claims the right to speak, atomically across replicas.
Broadcast. meeting_hub.broadcast publishes to Redis; every replica's listener delivers it to its own sockets, filtered per connection (§17).
Track. A nudge_created analytics event, wrapped in its own try/except: pass — instrumentation must never break the thing it instruments.
The cooldown is a SET NX, and that is the point redis.set(key, "1", nx=True, ex=120) returns whether it created the key. Checking "has it been 2 minutes?" and then setting the marker as two separate operations is a race that lets two replicas both decide to speak — and Donna talking over herself is a far more visible failure than a missed nudge. Read-then-write is a bug; the atomic form is the same line of code.

Cost Engineering — Why a Meeting-Hour Doesn't Bankrupt You

A naive implementation of "nine agents per utterance" pays for nine LLM calls per spoken sentence — a meeting-hour would cost dollars. Donna's typical utterance costs $0. Four mechanisms, in order of impact:

Deterministic gates before every model call. Regex/token matchers decide whether an LLM is even consulted: decision language for scribe, claim patterns for fact-check, similarity floors for insight, and six of nine hot agents never use an LLM at all. The gates are eval-tested with recall-biased floors (§23) — cheap must not mean blind.
Model tiering. MODEL_FAST (gpt-4o-mini, ~15× cheaper) for every structured extraction/classification — 14 of ~18 call sites. All env-swappable — a model upgrade is config, not a refactor.
Caching. Embedding cache (24h, deterministic), RAG response cache (5min, owner-keyed), per-claim fact-check cooldowns, spoken-nudge cooldowns, dispatch burst coalescing. Repeat work is the silent cost killer; every repeat has a named cache.
Metering. Every LLM call records model + token usage into a per-meeting Redis hash in micro-USD (core/llm_meter.py), surfaced at GET /{id}/cost and as a UI chip. You cannot price a product on costs you don't measure — this is the input to unit economics, not an afterthought.

Three properties of that snippet are worth copying, and one is worth criticizing:

✅ Per-agent attribution

agent:<name>:tokens means the cost readout decomposes by agent. "Which agent is expensive?" is answerable without new instrumentation — and it is the question you actually ask.

✅ Integer micro-USD

Redis hashes increment integers atomically. Storing dollars as floats would need read-modify-write, which is both slower and racy across replicas.

✅ Unknown models fail expensive

The .get(model, (2.50, 10.00)) default is the gpt-4o price, not zero. An unrecognized model over-reports rather than silently reporting free — the safe direction for a cost estimate to be wrong.

⚠️ Prices are hard-coded

The comment says "update alongside model changes," which is a process guarantee protecting a data guarantee. Provider price changes silently make every historical and current figure wrong, with nothing to detect it. §29.

Q: So what does an hour actually cost? The honest answer is that the system will tell you per meeting (GET /{id}/cost) but no representative figure has been recorded and published here. Publishing a number from a scripted demo meeting would be worse than publishing none — demo transcripts are unusually decision-dense, which inflates exactly the agents that cost money. The mechanism is built; the benchmark meeting is not. Marked instrumented, not characterized in §05.

The Meeting Journey, and the Calm Live Screen

Two redesigns, one principle: show the user the thing they are doing, and nothing else. The first replaced an accordion with a journey; the second replaced a dashboard with a single orb. Both were driven by the same observation — density is not the problem, undirected attention is.

From accordion to journey

The meeting page originally stacked all four phases — Knowledge Base, Research, Live Meeting, Summary — as collapsible panels on one screen. The failure was not that it was cramped. It was that nothing told the user what to do next: four panels of equal visual weight present four equally-plausible actions, so the interface asks the user to plan rather than to proceed.

RuleWhy
One step fills the screenA persistent rail answers the two questions the accordion left implicit: where am I, and what is left.
Soft-gating, not hardDocuments and research are genuinely optional, so those steps offer "Skip for now" rather than blocking. Only the summary is hard-locked — it cannot exist before the meeting ends — and it says so rather than silently refusing.
Honest button labelsThe CTA reads "Continue to Research" only when the step is actually satisfied; otherwise it reads "Skip for now". Calling a skip a completion is a small lie the user discovers later, on the summary screen.
Back is always allowedCompleted steps stay clickable. A journey permits return; a cage does not.
Auto-advance on real state changes onlyWhen the meeting goes live or ends, the user's task has genuinely changed, so the screen follows. It stops the moment the user navigates themselves — a background refresh must never yank the screen out from under someone mid-task.

The live screen: one orb, two buttons

The live view was a dashboard — transcript feed, nudge list, filters, controls — and every element of it competed with the conversation. But during a meeting the user is talking to people, not operating software. Anything on screen that asks to be read is a tax on the attention they owe the room.

🔮 The orb carries state

Warm grey and still when idle; cool blue and breathing while listening; a violet shimmer while an agent is working. Colour and motion replace a status panel entirely.

💬 Insights announce, then retire

A new insight arrives as a toast and then collapses into a counter. Nothing accumulates on screen demanding to be read.

👆 Two affordances

Ask Donna and Insights. Both are deliberate taps that open a panel over the calm — never inline clutter.

Why the motion is slow The orb breathes on a 6-second cycle and its halo on 10. A fast pulse reads as urgency, and urgency is the wrong feeling for something that sits in the corner of a conversation for an hour. Animation timing is a tone decision, not a decoration.
The mistake worth recording: a mockup is not a deletion order The design direction showed an orb and two buttons. Implemented literally, that removed voice capture itself — along with the transcript, agenda progress, and the type-an-utterance box that is the only way to exercise the agents without a working microphone. The correct reading was that the mockup describes the resting state, not the total feature set. Detail moved behind the panel (a third "Transcript" tab), not away. When a visual direction appears to delete a capability, it is describing a default, not a decision.

Errors have to say something actionable

A document that failed processing rendered as the single word "failed". The backend knew exactly why — an exhausted API quota — and said nothing. The UI now translates the stored error into the next action:

Read 1.0 with suspicion, not satisfaction Five suites at a perfect score across 96 cases means one of two things, and they are very different: either the gates are genuinely solid, or the datasets have stopped being hard enough to be informative. These datasets were authored alongside the fixes for the bugs they caught (§30) — a dataset written to characterize known failures will, by construction, be passed by the code that fixed them.

The metric to watch is not the score. It is how long since a case was added that the implementation failed. A suite that has not gone red in months is either finished or asleep, and there is no way to tell from the number alone.
What a healthy dataset looks like Roughly 10–20% of cases should be ones the current implementation gets wrong, sitting below a floor set at the current pass rate. That converts the suite from a regression alarm into a to-do list with a score attached, and it means the floors ratchet because the code improved rather than because the questions got easier. Growing these datasets with genuinely adversarial utterances — sarcasm, conditional commitments, decisions expressed as questions — is the highest-value measurement work available in this codebase.

Skip ≠ error ≠ pass, and why that distinction is load-bearing

The harness reports three outcomes, and collapsing any two of them produces a specific failure mode:

⏭ SKIP

A requirement is missing (no API key, no local embedder). The reason is printed and the gate is unaffected. If skip counted as pass, a CI environment without secrets would report a fully green intelligence layer while testing none of it.

💥 ERROR

The suite ran and blew up — exhausted quota, network failure. If error counted as skip, an expired API key would quietly disable your quality gates for weeks, and you'd find out from users.

✅ OK

It ran and the floors held. Metrics and per-case failure IDs land in the report either way, so a pass that nearly failed is still visible in the artifact.

What Is Still Unmeasured

The chapter most architecture documents omit. Everything below is a real gap between what this system claims and what it can prove. They are ordered by how much a wrong answer would cost.

1 · Answer groundednessclosed

Retrieval quality is measured (MRR, nDCG, Recall@k). Whether the generated sentence is actually supported by the chunks it cites is not measured at all. Donna can retrieve perfectly and still assert something the source does not say — and because the answer arrives with a citation attached, a hallucination is more credible than it would be without one. Provenance without groundedness is a confidence amplifier pointed at an unverified claim.

Closed. services/rag/groundedness.py is a deterministic checker — no model call, microseconds — targeting the failure mode that actually hurts: fabricated specifics (a number, date, amount or name asserted in the answer but absent from the context). It runs in three places at once, which an LLM judge could not: inline on every RAG answer (a groundedness field on the response), as a CI-gated suite of 30 human-labelled cases, and as a debugging tool. Measured: detection recall 0.93, false-alarm rate 0.00 — the latter ceiling-gated, because a checker that cries wolf gets switched off, and a switched-off checker detects nothing.

Known limit, deliberately not papered over: it cannot catch semantic contradiction where the vocabulary matches but the meaning inverts ("rollback is manual" → "rollbacks are fully automated"). That case sits in the dataset failing, and hard_case_accuracy is reported but ungated. ADR-012 records when an LLM judge would earn its latency.

2 · Nudge acceptance rateendpoint shipped

Partly closed. GET /api/v1/meetings/nudge-acceptance now reports, per agent: pinned, dismissed, ignored, acceptance rate (pinned / (pinned + dismissed) — deliberately excluding ignored, so it measures "when someone acted, did they keep it?"), engagement rate, and a sufficient_data flag at ≥20 explicit actions so a 2-of-2 row cannot masquerade as a signal.

What remains is not engineering: the endpoint needs real usage pointed at it, and then someone has to act on what it says. A metric nobody reads is the same as a metric nobody has.

Why it matters more than it looks: §06 leaves the Neo4j decision explicitly open pending this number. Two agents and an entire datastore are justified by a hypothesis that the existing telemetry could confirm or kill this week.

3 · End-to-end nudge latencyclosed

The "< 2 s to first insight" claim is structural: the activation agent has a 2 s timeout and does no I/O, so it cannot exceed it. But the budget covers only agent execution — not STT finalization, not the HTTP POST, not the queue hop, not persistence, not WS delivery. The number a user experiences is the sum of a pipeline that has never been timed end to end.

Closed. The utterance endpoint stamps an acceptance time in Redis; the dispatcher stops the clock as each nudge is broadcast. Three histograms: first_nudge_seconds (time to first insight), nudge_end_to_end_seconds{agent,nudge_type} (per agent), and dispatch_queue_wait_seconds — the last isolating queue time so "the agents were slow" and "nothing was draining the queue" stop looking identical. Timing is best-effort with a short TTL: a stale start time would report a fictional latency, so a lost measurement is preferred to a wrong one.

4 · Transcription accuracyvendor-trusted

No WER measurement against a labelled corpus. Every downstream agent consumes STT output as ground truth, so transcription error is the noise floor for the entire product — and it is unknown. It is also the failure mode users notice first, because they can see the transcript and know what they said.

5 · Behaviour above one replicarunnable, still unobserved

The distributed lock, the pub/sub bridge and the stateless workers are all built for horizontal scale, and none of it has been run on more than one backend replica. The mechanisms are individually the standard ones; the composition is untested. The specific thing that would surface first is duplicate nudges under a Redis blip, since the lock's fallback is process-local (§15).

Now one command away. docker compose -f docker-compose.yml -f docker-compose.replicas.yml up -d --scale backend=2 brings up N replicas behind an nginx that actually upgrades WebSockets (without the Upgrade headers the live board dies silently while health checks stay green). The overlay's header comment lists exactly what to watch. Circuit-breaker state is also Redis-shared now, so one replica tripping opens the circuit fleet-wide. Still unobserved — the mechanism exists; nobody has run it under load.

6 · Cost per meeting-hour, characterizedtooling shipped

The meter works and reports per meeting. What is missing is a representative figure — a real meeting of known length and decision density, measured and published, so that "a meeting-hour costs roughly X" becomes a fact rather than an argument from mechanism.

The tool now exists: scripts/characterize-cost.py replays a transcript through the real dispatcher and reads the per-agent breakdown out of the meter — so the figure includes the gates, which an estimate from call-counts would get wrong. It prints its own caveat: a scripted transcript is unusually decision-dense, so the output is an upper bound unless the transcript is genuinely representative. What remains is running it on real usage.

Why publishing this list is the point Every one of these gaps is discoverable by a competent reviewer in an afternoon. Naming them first converts a credibility risk into evidence of judgement — and, more practically, it is how the list gets shorter. Unnamed gaps do not get closed; they get discovered during a customer conversation.

Q: What would horizontal scale look like? The circuit breaker, and the state it exposes

core/resilience.py combines retry, breaker, timeout and Prometheus instrumentation into one decorator. The breaker is a three-state machine with a detail worth noting — the state is computed on read, so recovery needs no timer:

apps/api/core/resilience.py — CircuitBreakerOPEN → HALF_OPEN happens lazily
@property def state(self) -> str: if self._state == "OPEN": if time.monotonic() - self._last_failure_time >= self.recovery_timeout: self._state = "HALF_OPEN" # no background task needed return self._state # defaults: failure_threshold=5, recovery_timeout=30.0s # Global registry so /health can report every breaker's state: def get_all_breaker_states() -> dict[str, str]: return {name: cb.state for name, cb in _breakers.items()}

Why lazy state matters

No timer, no background task, no cleanup. A breaker that needs a scheduler to recover is a breaker that stays open forever the day the scheduler dies — which is precisely when you need it to recover.

Why the registry matters

/health reports every breaker's state, so "OpenAI is down" is a fact the health endpoint asserts rather than something you infer from a log spike. The frontend's "intelligence degraded" banner reads from it.

One honest caveat about the breaker _breakers is a module-level dict — breaker state is per-process. With N backend replicas, each learns independently that OpenAI is down, so the fleet collectively sends up to N × failure_threshold doomed requests before all of them open. Correct enough at current scale, and a genuine (small) problem at replica counts this deployment has never run — noted in §29 rather than pre-emptively solved with a distributed breaker nobody needs yet.

Arq queue fairness2nd concurrent tenant One user's 100-document batch delays another user's live dispatch job. Not modelled today — Arq has no priorities or per-tenant fairness. Dispatch jobs and document jobs share one queue. First fix is separate queues by latency class, which is a config change; real fairness needs a different queue.
PostgresWrite volume on nudges Insert latency on the emit path; the hot path starts feeling the transactional DB. Read replicas for the dashboard/open-items queries first. Transcript appends are per-meeting row locks, so they shard naturally and are not the bottleneck.
QdrantCorpus size per tenant Retrieval p95 rises; the context agent starts hitting its 10 s budget. Payload-indexed owner_id filtering already scopes each search. Next steps are collection sharding and quantization — neither needed until a single tenant's corpus is large, and the 10 s timeout means degradation shows up as missing context nudges, not as a slow meeting.
RedisFive roles competing Pub/sub latency rises during queue bursts; the <50 ms fan-out budget erodes. Split by role — queue onto its own instance first, since it has the burstiest and least latency-sensitive traffic. See §06's revisit conditions.
LiveKitConcurrent rooms Audio quality degradation, join failures. Standard SFU scaling, or move to LiveKit Cloud. Independent of everything else here.
OpenAI rate limitsConcurrent meetings × LLM agents Breakers open; the degraded banner appears for everyone at once. The gates already suppress most calls. Beyond that: per-tenant rate budgets, and a request-level queue in front of the smart tier so summaries yield to live nudges.
The property that makes all of this tractable Every scaling limit above degrades into fewer or later nudges rather than into a broken meeting. That is not luck — it is the direct payoff of driver 3 and invariant 4. When the intelligence layer is architecturally optional, capacity planning stops being a correctness problem and becomes a quality-of-service problem, which is a much easier thing to be wrong about.
Honest framing Every row past "backend replicas" is reasoned from mechanism, not observed under load. The mechanisms are individually standard and individually sound; the claim being made is that the design does not preclude these moves, not that they have been performed. No load test has been run above a single replica.

The Defect Register

Severity-ranked defects found by review rather than by a failing test — the class that comes back if nobody writes one. D2–D7 have since been fixed and are kept here, struck through, with what shipped: a register that only ever grows is a list, but one that shows items closing is a process. Each fix is pinned by a regression test in tests/unit/test_defect_regressions.py. D1 and D8 remain open.

D1 · No backup, no restore drillseverity: high

Postgres, Qdrant and MinIO are Docker volumes with no automated backup, no offsite copy and no tested restore path. RPO and RTO are both undefined. Every other item in this register is recoverable; this one is not.

Partially addressed. Three scripts now exist: scripts/backup.sh (Postgres custom-format dump + MinIO objects + Qdrant snapshots + optional Neo4j, with a SHA-256 manifest, and a hard failure if the Postgres dump is implausibly small — a truncated dump that looks like success is worse than no dump), scripts/restore.sh (verifies the manifest before touching anything live, and requires explicit confirmation), and scripts/verify-backup.sh — a real restore drill into a throwaway Postgres container that asserts tables and rows actually came back.

Now scheduled. .github/workflows/backup-drill.yml runs backup → destroy → restore → assert seeded rows came back every Monday and on any change to the scripts or migrations. It asserts on outcomes, not on the absence of errors — pg_restore warns routinely, and "no errors" is not "data present".

Still open: the drill exercises the procedure, not production data. Nothing schedules a backup of the real stack, and there is no offsite copy. The remaining work is deployment-shaped (managed Postgres with PITR, object-store replication, a cron that runs the drill and alerts on failure). First real customer makes this blocking. An unverified backup is a hypothesis — the drill exists now, but a drill nobody runs is the same hypothesis.

D2 · Tenant isolation in dev mode rests on configurationfixed

With REQUIRE_AUTH=false, requests are ownerless and the RAG cache key falls back to 'global' (§10). Isolation then depends on an environment variable being right, rather than on a mechanism that cannot be misconfigured. Every check is written as "if a user is present, enforce" — which is exactly the shape that silently permits everything when no user is present.

Fix shape: refuse to boot with APP_ENV=production and REQUIRE_AUTH=false together. A ten-line startup assertion converts a configuration hazard into an impossible state.

Fixed. Production now refuses to boot when APP_ENV=production is combined with REQUIRE_AUTH=false or a default JWT_SECRET — settings.assert_production_safe() runs in the lifespan before any service connects. The unsafe state is now unrepresentable rather than merely discouraged. Pinned by tests/unit/test_defect_regressions.py and a dedicated CI gate.

D3 · Activation nudges are addressed by display namefixed

_visible_to() matches source_data.person against the connection's name, lowercased (§17). Two attendees sharing a first name would each receive the other's private expertise nudges — a real, if narrow, privacy leak, and one that gets more likely as meetings get larger.

Fix shape: key activation on attendee email, which is already the identity used for participant access via JSONB containment. The data is there; the matcher just uses the wrong field.

Fixed. Activation nudges now carry source_data.person_email, and both privacy filters (MeetingHub._visible_to for WS, _visible_nudges for REST) match on it. Name matching survives only as a fallback for pre-existing nudges, and only when the connection has no email. Two attendees named "Chris" no longer see each other's private nudges — regression-tested both ways.

D4 · Circuit-breaker state is per-processfixed

_breakers is a module-level dict, so each replica learns independently that a provider is down. At N replicas the fleet sends up to N × 5 doomed requests before all breakers open, and a recovering provider gets probed N times at once.

Why it's still open: harmless at one replica, and a distributed breaker (Redis-backed counters) is real complexity to buy back a problem this deployment does not yet have. Becomes worth fixing at the same moment §25's multi-replica gap does.

Fixed. Breaker trips are now shared through Redis: the first replica to open a circuit opens it fleet-wide, and the half-open probe is claimed by exactly one caller via SET NX so a recovering provider is not stampeded. Entirely best-effort — with Redis unavailable, behaviour falls back to the previous per-process semantics.

D5 · Model prices are a hard-coded tablefixed

_PRICES in llm_meter.py carries a comment reading "update alongside model changes." When a provider changes pricing, every historical and current cost figure silently becomes wrong, with no mechanism to detect the drift. Unknown models default to gpt-4o pricing, which at least fails expensive rather than free.

Fix shape: stamp the price table version into each meeting's cost hash, so a figure can at least be re-derived later — and so a stale table is visible in the data rather than invisible.

Fixed. Each meeting's cost hash is now stamped with PRICE_TABLE_VERSION, and GET /{id}/cost returns price_table_current plus an unpriced_calls counter. A stale table is now visible in the data instead of invisible, and an unknown model logs a warning naming the model to add.

D6 · The Arq queue has no priorities or fairnessfixed

Strict FIFO, one queue for all job types. A 100-document upload batch queues ahead of the live dispatch_job for a meeting that is currently happening — so a cold-path bulk operation can starve the hot path, which inverts the entire temperature model the architecture is built on.

Fix shape: separate queues by latency class (dispatch on its own, everything else shared) — a config change, and worth doing before the second concurrent tenant, not after.

Fixed. Split into two queues by latency class: donna:hot (dispatch_job only) and donna:bulk (research, summary, document processing), consumed by two separate worker processes (DispatchWorkerSettings / WorkerSettings). A bulk upload batch can no longer occupy the slots a live meeting needs. Unknown jobs default to bulk, and /health reports per-queue depth so an unconsumed queue is visible rather than silent.

D7 · Broad exception handlers can still hide real errorsfixed

Best-effort paths (metering, analytics, learned-mute, speak) swallow everything by design — correctly, since none may break a meeting. But several log at debug level, which in production JSON logging at INFO means they log nowhere. This is the exact shape of the jsonpath bug in §30, which was invisible for the same reason.

Fix shape: best-effort paths should log at warning with a rate limit. Silence is only acceptable when the failure is genuinely expected, not merely tolerable.

Fixed. The degradation paths that hid real failures — Redis lock fallback, pub/sub publish failure, all five cache paths, and the memory/KG/flow agent skips — now emit at WARNING via warn_throttled(): at most one line per key per 60s, with the suppressed count appended so the true rate stays visible. Genuinely expected paths (NLTK fallbacks, dead-socket pruning) deliberately stay at debug.

D8 · Deepgram SDK is pinned below a major versionseverity: low

Pinned >=3.7,<4 because v4 removed the streaming client the voice worker uses. A working pin, and also a deferred migration that gets more expensive the longer it sits — security patches for the 3.x line will not continue indefinitely.

D11 · Customer database integration is untested against a real databaseseverity: high

Every guard in §11 is unit-tested adversarially (74 cases: SSRF, SQL injection, stacked statements, table escape, column leakage, secret handling) and verified live inside the running container. But the feature has never been pointed at a genuine third-party Postgres. The guards are proven; the integration is not — connection handling, TLS negotiation against a real certificate, introspection on a large production catalog, and the write-probe against a real least-privilege role are all unexercised.

Why it's still open: it needs a database that is not ours. Blocking before any customer connects one.

D12 · Snapshot sync is manualseverity: medium

In-meeting facts come from an indexed snapshot (§11), and the snapshot is refreshed only when someone presses "Sync". So the freshness guarantee is "as recent as the last time a human remembered" — which for a feature whose value is factual grounding is a quiet way to become wrong.

Fix shape: an Arq cron on the bulk worker, with the last-sync age surfaced on /health the way the outbox lag already is.

D13 · Only PostgreSQL is supportedseverity: low

asyncpg was already a dependency and Postgres covers most of the target market, so it shipped first. MySQL, SQL Server and Snowflake are all common in the companies this feature is for. The connector is written against a driver seam, so this is an addition rather than a redesign — but every guard that is Postgres-specific (session READ ONLY, statement_timeout, the pg_* function denylist) needs a per-engine equivalent, and "we ported it" must mean "we ported the guards".

D10 · Model registry gap silently broke analyticsfixed

models/__init__.py was empty, so importing one model did not register the others. Analytics INSERTs failed foreign-key resolution and were swallowed — intermittently, depending on which requests had run first. Full story in §30.

Fixed. The models package now imports every model, so any entry point gets a complete metadata registry with no discipline required at the call site. Pinned by three tests, including one that walks every foreign key and fails if any target is unregistered.

D9 · The CI drift gate could never passfixed

Found while adding the outbox migration, and older than it: migration f3a9d82c41b7 created the calendar index as ix_meetings_external_event_id, but Base.metadata declares "ix": "ix_%(column_0_label)s" and the table is schema-qualified — so SQLAlchemy expected ix_doc_intel_meetings_external_event_id. alembic check therefore reported a permanent remove-index/add-index diff.

The consequence was not cosmetic. CI's "check for model/migration drift" step is the gate that catches a model change shipped without a migration, and it was red on every run — which means it was either failing the build constantly or being ignored. A gate that is always red is a gate nobody reads.

Fixed. Migration b4d1f7a2c8e3 renames the index to match the convention (a catalog rename, so the index is never unavailable), and alembic check now reports "No new upgrade operations detected" for the first time. Principle: a quality gate that cannot pass is worse than no gate, because it trains people to skip it.

D14 · Research briefs accumulated, and the read picked an arbitrary oneseverity: high · fixed

Meeting.research_brief is declared uselist=False, but the pipeline inserted a new row per run. One meeting held eleven briefs, three of them successful; the unordered relationship returned the oldest — the original failure — so every retry worked and the UI never showed it. A second query used scalar_one_or_none(), which raises on multiple rows: a latent crash awaiting the first meeting researched successfully twice.

Fixed at three levels: the pipeline reuses one row per meeting, the relationship orders newest-first so existing duplicates resolve correctly, and the second query takes .first() over an ordered set. See §34.2.

D15 · Background-job buttons cleared their loading state on request completionseverity: medium · fixed

Research and summary both cleared loading in a finally that ran when the POST resolved — about 20ms — then refetched once after a guessed delay. Measurement: the summary POST returns in 0s and the summary is ready at 17s, so the 3s refetch was fourteen seconds early on every single run. The only way to see a summary was a manual page reload.

Fixed by polling to a terminal state with a bounded timeout, and by committing the screen to a "working" state rather than re-offering the button already pressed. The better fix — emitting completion events on the existing meeting WebSocket — is recorded in §34.3 and not yet built.

D16 · The voice worker's TTS subscriber died 3ms after subscribingseverity: high · fixed

The LiveKit job held itself open with await ctx.wait_for_participant(), which returns immediately because the agent is dispatched because somebody joined. The finally block then tore down TTS. Spoken replies were published to a Redis channel with no subscriber — and a publish to nobody is a successful publish, so nothing anywhere reported an error while Donna was completely inaudible.

Fixed by waiting on a room-disconnect event. Two related defects in the same file: _prewarm was unreachable from forked job subprocesses (defined under if __name__ == "__main__"), and once moved, still had to become synchronous because LiveKit invokes it without awaiting. See §34.4.

D17 · Viewer-relative speaker labels persisted into shared transcriptsseverity: medium · fixed

my_name resolved only from the attendee list, and a meeting owner is not normally an attendee of their own meeting — so it returned null and the client stored the literal string 'You' as the speaker. A transcript is a shared artifact: every other reader, and every summary-email recipient, sees "You" meaning somebody who is not them.

Fixed by falling back past the attendee list to the account, and by having the server override viewer-relative labels with the authenticated user's real name so a buggy client cannot poison the record. See §34.6.

D18 · Semantic duplicate insights are not suppressedseverity: low · open

Nudges now dedupe on a normalized content fingerprint within a 15-minute window, which removed the case where one finding became nine cards. A genuinely reworded restatement of the same finding still gets through.

Why it's still open: semantic deduplication requires an embedding comparison per nudge on the live dispatch path, which is real latency spent on a problem that has not yet been observed in practice. Worth building when it is, not before. See §34.7.

How to read a register like this The useful signal is not the count — it is whether the severities are honest and whether the "why it's still open" lines describe real trade-offs rather than procrastination. D1 and D2 are the two that would genuinely change a buying decision; both are named first, in plain language, without softening. D14–D17 were all found by a user testing the product rather than by review or by CI, and every one of them was a case where the backend worked and the result never reached the screen — which is why they earned a chapter of their own (§34) rather than a line each.

War Stories — Real Bugs, and the Principles They Encode

Every bug below actually happened in this codebase, was found by its own tests/evals/smoke runs, and got fixed the same day. Each teaches something a tutorial won't.

The config that silently wasn't Pydantic v2 ignores the v1-style Field(env="APP_ENV") kwarg — so APP_ENV=production in Docker had never actually set environment. When the fields were migrated to validation_alias=AliasChoices(...), production mode engaged for real for the first time — and immediately exposed a second latent bug: the engine builder combined NullPool with pool sizing kwargs, an invalid pairing that crashed on boot (and NullPool is wrong for an API anyway — a fresh TCP connection per checkout). Principles: deprecation warnings are load-bearing; and config that silently no-ops is worse than config that crashes.
The worker that couldn't reach the database — quietly Compose gave the job-worker DATABASE_URL, but the engine builds its DSN from POSTGRES_HOST/PORT/… parts. The worker connected to localhost inside its own container, failed, logged, and the dispatch job "completed." Found only by a live smoke test asserting on outcomes (did the agenda flip to covered?) rather than logs. Principles: know which env vars your code actually reads; and smoke tests must assert results, not absence of errors.
The cache that would have leaked between tenants The RAG response cache was keyed on query + context_level — correct when retrieval was global, silently wrong the day retrieval became owner-scoped: user B could receive user A's cached answer verbatim. Caught in a criticality review, fixed by putting the owner in the key. Principle: a cache key must contain every input that changes the answer — and "who is asking" became an input the moment tenancy shipped. Re-audit caches whenever scoping rules change.
The barrier that made fast agents slow The original dispatcher used asyncio.gather — every nudge waited for the slowest agent, so a 200ms activation match arrived after a 20s web search. The fix (as_completed + per-agent timeouts) required restructuring emission to be per-result — which then surfaced the next bug: the DB session opened for state loading was held across the whole 25s fan-out, pinning a pool connection per active meeting. Principles: barriers are a smell in latency-sensitive fan-outs; and never hold a pooled connection across slow I/O you don't control.
The jsonpath that wasn't a jsonpath Slicing the transcript server-side ($[last-11 to last]) failed with "function jsonb_path_query_array(jsonb, character varying) does not exist" — SQLAlchemy bound the path string as varchar; Postgres wanted the jsonpath type (cast(literal(...), JSONPATH)). Worse: the error was swallowed by a defensive except that returned None, so dispatch just… did nothing. Found live, again by outcome-asserting smoke. Principles: broad exception handlers around SQL turn errors into silence — log loudly; and exercise new SQL against a real database, not just mocks.
The binary that Redis would have mangled Packing embedding vectors as raw float32 bytes would have corrupted them — the shared Redis client runs decode_responses=True, which UTF-8-decodes everything. The cache stores base64-wrapped float32 instead (~4× smaller than JSON, text-safe), with a legacy-JSON fallback on read. Principle: know your client's decoding contract before storing non-text; migration paths beat flag-day format changes.
The ORM objects that expired mid-flight Analytics tracking committed the session — expiring loaded ORM objects — after which the endpoint touched their attributes: MissingGreenlet, the async equivalent of a lazy-load ambush. Fix: capture response values before the tracking commit; the session factory also runs expire_on_commit=False. Principle: in async SQLAlchemy there is no implicit lazy anything — read what you need, then commit.
The regex that couldn't see money The fact-check gate's \b(\$\s*\d|…) never matched "$99" — a word boundary can't exist between a space and "$" (both non-word). Nobody noticed until the eval harness's golden dataset scored the gate at 0.73 recall on day one and the failure IDs pointed straight at it. Principles: regex word boundaries only work adjacent to word characters; and untested heuristics rot invisibly — golden datasets make them visible.
The 409 that punished failure twice Upload dedupe rejected any duplicate content hash — including documents whose previous processing had failed. Users couldn't retry the exact file that needed retrying. Fix: a failed duplicate deletes the dead rows and reprocesses. Principle: dedupe on (content, outcome), not content alone — idempotency must account for failure states.
The agent rebuilt on every request The enhanced query path constructed its voice agent per request — paying initialization every call and silently wiping its in-memory conversation contexts, so multi-turn continuity never worked. Same class of bug, cold path: the doc-processing job rebuilt Docling/OCR models per document. Both became lazy singletons. Principle: any object that is expensive to build or holds session state must have an owner with a lifetime — "constructed where used" is not a lifecycle.
The schema with two owners A fresh Postgres volume could never boot. init-db.sql, mounted into docker-entrypoint-initdb.d, created five tables — documents, document_chunks, contextual_embeddings, conversation_sessions, analytics_events — and the container's CMD then ran alembic upgrade head, whose initial revision creates the same tables. Result: DuplicateTableError: relation "conversation_sessions" already exists, crash-loop. It had only ever worked on volumes that predated the migration. Principle: a schema has exactly one owner. Two mechanisms that both "helpfully" create tables are not redundancy, they are a contradiction that surfaces on the first clean install. The init script now creates the schema and extensions only.
The foreign key that was fine until it wasn't imported Analytics silently wrote nothing. AnalyticsEvent.document_id declares ForeignKey("doc_intel.documents.id"), but main.py imported the Document model only inside function bodies — so at startup 14 tables were registered instead of 18, and doc_intel.documents was not among them. SQLAlchemy resolves foreign keys at statement-compile time, so every analytics INSERT failed FK resolution and was swallowed by track_event's except-and-log. Worse than a plain failure: it was order-dependent, starting to work after any request that happened to import Document. Principle: importing any model must register all of them. The fix is a populated models/__init__.py, so no call site needs to remember. A regression test now walks every FK in the metadata and fails if any target is unregistered — catching the class, not the instance.
The port that was the wrong protocol The voice assistant failed with ConnectionError: could not establish pc connection. Signalling worked, ICE negotiated, then nothing. The compose file read - "7882:7882" # RTC/UDP — but Docker's port syntax defaults to TCP, so the comment described an intent the configuration did not implement. WebRTC media is UDP; there was nowhere for it to flow. Principle: a comment is not configuration. When a line's comment states a protocol, check that the syntax actually selects it — docker port tells you the truth in one command.
The gate that could never pass Found while adding an unrelated migration: alembic check had a permanent diff. Migration f3a9d82c41b7 created an index as ix_meetings_external_event_id, while Base.metadata declares "ix": "ix_%(column_0_label)s" on a schema-qualified table — so SQLAlchemy expected ix_doc_intel_meetings_external_event_id. The CI drift gate, whose entire job is catching a model change shipped without a migration, was red on every run and therefore being ignored. Principle: a quality gate that cannot pass is worse than no gate, because it trains people to skip it.

The pattern behind the pattern

Fourteen stories, and most share a single shape: something failed, and the failure was invisible. Config that no-op'd. A worker that logged and reported success. A cache that returned the wrong tenant's answer with full confidence. A jsonpath error swallowed into None. A regex that never matched money. In every case the code was "handling" the error — and handling it by making it inaudible.

If you take one thing from this chapter The bugs that cost the most were not the ones that crashed. They were the ones that returned plausible-looking nothing. Every except block is a decision about what you are willing to not find out about — and in a system where the output is suggestions rather than answers, "no suggestion" looks identical to "nothing to suggest." That ambiguity is the enemy, and it is why §29 D7 stays on the register.

The Review Checklist

What to actually look for when reviewing a change against this architecture. Each item maps to an invariant (§04) or a bug that already happened (§30) — nothing here is style preference.

Any change touching retrieval or cachinginvariants 1, 2
  • Does every new Qdrant write include owner_id in the payload, and every read filter on it?
  • Does the cache key contain every input that changes the answer — including who is asking?
  • If scoping rules changed at all, were all cache keys re-audited, not just the one being edited?
  • Is anything non-text being stored in Redis? The client decodes responses — it must be base64 or it will be corrupted silently.
Any change to the dispatcher or an agentinvariants 4, 5
  • Is the fan-out still as_completed? A gather is a latency regression that no test will catch.
  • Does the new agent have an entry in _AGENT_TIMEOUTS, tiered by what it touches?
  • Does it degrade to None on every failure path, so it can never take the cycle down?
  • Is a DB session held across any I/O the process does not control?
  • If it calls an LLM: is there a free deterministic gate in front, and does that gate have golden cases?
  • If it emits nudges: is there a cooldown, and is it an atomic SET NX EX rather than read-then-write?
Any change touching realtime deliveryinvariant 3, §17
  • Does _visible_to() still default to deny for participants?
  • Does a new event type need filtering, or is "all participants see it" genuinely correct?
  • Is the filter server-side? Anything hidden only in the client is not hidden.
Any change to configuration or schemainvariants 6, 9
  • Does the code read the env var you think it reads? (Both DATABASE_URL and POSTGRES_* exist; the engine uses the parts.)
  • Is a Pydantic field using validation_alias=AliasChoices(...)? The v1-style Field(env=...) is silently ignored in v2.
  • Does absent config degrade to a feature being off, or does it crash?
  • Is there an Alembic revision? CI runs alembic check and a model change without one fails the build.
Before merging anythingthe meta-check
  • Is there an except that now swallows something worth hearing about? Log it at warning, not debug.
  • Does any test assert on the absence of errors rather than on an outcome? Rewrite it to assert the outcome.
  • If this change makes a quality claim, is there a gate that would go red when the claim stops being true?
  • Did anything in §05's status table just change status — in either direction?

Chapter 33 · Resilience

The Fallback Path — Running Without OpenAI

OpenAI is a hard dependency of nearly every path in this system: the 19 agents, the query planner, the RAG synthesiser, the embedding pipeline. When the account's credit balance hit zero, all of them returned 429 and the product stopped end to end. This chapter is the fallback that closed that, and — more interestingly — the several ways a naive version of it would have been worse than the outage.

33.1 · The asymmetry that drives the whole design

The tempting framing is "swap the base URL and carry on". Ollama speaks the OpenAI wire protocol at /v1, so at the transport layer that is genuinely all it takes. The framing is wrong because it treats two very different operations as one.

Chat is safe to fail over. Text in, text out. A weaker model gives a worse answer, but a worse answer is the same kind of thing. Nothing persists, nothing is corrupted, and the next call can go straight back to OpenAI.

Embeddings are not. An embedding is meaningful only relative to other embeddings from the same model. text-embedding-3-small emits 1536 dimensions; nomic-embed-text emits 768. Even at equal width the axes would be unrelated — cosine similarity between vectors from two different models is noise wearing the costume of a score. Writing Ollama vectors into a collection built from OpenAI vectors does not degrade retrieval. It poisons it silently and permanently, in a way that keeps returning confident results with plausible scores. There is no error to notice and no symptom until somebody checks whether the answers are actually right.

This codebase already contained one instance of exactly that mistake. EmbeddingService zero-padded a 384-dim sentence-transformers vector out to 1536 so it would "fit" — it fits the way a wrong key fits a lock you have filed down. Two further sites pad-or-truncate a mismatched vector to the target width. All three were removed rather than extended; a vector reshaped to fit is not a worse embedding, it is a meaningless one that still scores against real neighbours.

One vector space per embedding modelcorrectness vs continuity of recall
Why
Collections are named after the model that filled them (llm_provider.collection_prefix()), so an Ollama vector physically cannot land in an OpenAI collection — and Qdrant rejects a 768-dim write into a 1536-dim collection anyway, so a mistake fails loudly instead of silently degrading recall. Failing over becomes an honest, visible, reversible degradation.
Beat
Padding to a common width (the existing bug, rejected); refusing embedding failover entirely (safe, but leaves indexing dead exactly when it is needed); a single collection with a model tag filtered at query time (works, but every query pays a filter and one forgotten filter reintroduces the corruption).
Trade-off
Content indexed under the other provider is not searchable while failed over. A corpus embedded with OpenAI goes invisible the moment Ollama takes over, and comes back untouched when OpenAI returns. That is a real capability loss, chosen deliberately over the alternative — which is not "no loss" but "loss you cannot detect".
Revisit when
If the fallback stops being an emergency and becomes a steady state, dual-writing both spaces during ingestion would keep both searchable at roughly double the embedding cost. Only worth it if failover duration starts being measured in days.

33.2 · Two Ollama endpoints, not one

The obvious implementation has one fallback. Probing the actual catalogue produced a fact that forced a split: Ollama Cloud publishes 18 chat models and zero embedding models. An embedding call there does not degrade — it 404s.

PathNormalFailed overWhy
Chat gpt-4o-mini / gpt-4o Ollama Cloud gpt-oss:20b / gpt-oss:120b Far closer to GPT-4o than anything that fits on a laptop.
Embeddings text-embedding-3-* (1536d) Local Ollama nomic-embed-text (768d) The only fallback that can produce a vector at all.

So active_provider() (chat) and embedding_provider() resolve separately, and during a failover the two legitimately point at different machines — chat in the cloud, embeddings on localhost. With no cloud key configured, chat falls back to local as well, so the system still works with no account and no network.

33.3 · What counts as a reason to fail over

The latch only arms on systemic failures — the kind that will recur on the next call regardless of the request. The distinction that matters most is inside HTTP 429: a quota 429 is systemic, because no amount of waiting refills an empty balance; a requests-per-minute 429 is transient, and treating it as systemic would silently demote the entire process to a local 3B model every time traffic spiked. A 400 on one malformed request is that request's problem and must never reroute the process.

33.4 · The failures that only appear under fallback

Getting the routing right made the system reachable. It did not make it work. Three separate layers had been tuned, implicitly, to the performance envelope of one specific vendor.

The circuit breaker followed the declared service, not the real oneprotection vs self-inflicted outage
Symptom
Circuit breaker OPEN for openai while every request was already being served by Ollama.
Cause
Agents declare @resilient_call("openai"). Under failover the request goes to Ollama, but a slow Ollama response recorded a failure against the OpenAI breaker — which then rejected calls that would have gone to Ollama anyway. The breaker ended up guarding a service nobody was calling while blocking the one that still worked.
Fix
_effective_target() resolves the real backend per call, so the breaker key and the timeout budget both follow the provider actually being used. Wrapped in a bare except that falls back to the declared values — this runs on every agent call and must never itself be the thing that breaks.
Trade-off
Breaker state is now per-backend, so a provider that has just recovered starts from a clean slate rather than inheriting the other's failures. That is correct, but it does mean the fleet re-learns each backend's health independently.
Two timeout layers, only one of them obviouslatency budget vs model reality
Symptom
Donna produced no insights at all under fallback, while the dispatcher reported every job complete and zero failed.
Cause
The per-agent budgets (insight: 12s, scribe: 12s) are enforced by asyncio.wait_for in the dispatcher — outside resilient_call. Raising the timeout inside the resilience layer changed nothing: the dispatcher cancelled the coroutine first, every LLM agent degraded to None, and "degraded to None" is indistinguishable from "had nothing to say".
Fix
_agent_timeout() scales LLM-bound agents by 4× under fallback, capped at 45s. Non-LLM agents (pure matchers, Neo4j traversal, one SQL aggregate) keep their original budgets — a slower chat model is no reason to let a graph traversal run longer.
Trade-off
A live nudge that lands after the moment has passed is worthless, so the stretch is bounded rather than open-ended. Under fallback, some nudges will now arrive too late to be useful instead of not arriving at all. That is a better failure, not a good one.

33.5 · Prompts are tuned to a model too

Every agent asks for JSON and calls json.loads on the result. GPT-4o complies closely enough that this works almost always. The fallback models do not, and they fail in two different ways that need two different answers.

llama3.2:3b answered this repository's own research prompt with unquoted string values — structurally invalid JSON that no lenient parser can honestly repair, because an unquoted value spanning commas and periods has no unambiguous delimiter. The fix is not parsing but prevention: Ollama supports grammar-constrained decoding, and _force_json_mode() enables it automatically whenever the prompt mentions JSON, which makes malformed output impossible rather than unlikely.

gpt-oss:120b — the large, capable model — emitted **rationale**:, markdown emphasis leaking into a JSON key. Constrained decoding alone would not have caught this, so apps/api/core/json_parse.py repairs the deviations that are unambiguous: fences, prose either side, trailing commas, Python literals, markdown-bolded and bare keys. It works on structure with string contents masked, so prose inside a value is never rewritten. It deliberately refuses the llama case — half-parsing a genuinely broken structure silently drops fields, which is worse than an error the caller can see.

The general lesson. Constrained decoding prevents the failure; the tolerant parser recovers what still slips through. Either alone leaves a gap — and both real failures were found by running the actual prompts against the actual models, not by reasoning about what models "usually" do.

33.6 · Speech-to-text was tuned to one vendor too

The same class of assumption sat one layer further out, and it is the one that made Donna unreachable by voice. Deepgram's default endpointing is 10ms, so it finalizes a segment at the slightest pause. One spoken question arrived as three utterances: 

[Nikhil Bindal] Donald,
[Nikhil Bindal] we did what did we decide about
[Nikhil Bindal] acne?

Two failures compounding. The name landed in the first fragment, the verb in the second, the object in the third — so no fragment was a question addressed to anyone. And "Donna" was transcribed as "Donald": the single token that determines whether the assistant knows it is being spoken to was the one the model got wrong. "Acme" became "acne".

Fixed at both ends: endpointing=400 so a speaker can breathe mid-sentence, and keyword boosting (Donna:3 weighted highest, plus the vendor names), extensible per deployment via DEEPGRAM_KEYWORDS. The reply agent additionally merges consecutive fragments from the same speaker before testing, so a question survives fragmentation even when STT still splits it.

Chapter 34 · Judgement

Silent Success — When Working Code Looks Broken

A run of bugs found in one testing session shared a single shape, and it is not the shape engineers usually look for. In every case the backend did the right thing, logged success, and returned 200 — and the user saw nothing. None of them would have been caught by a test that asserts the function returns the correct value, because in every case it did.

34.1 · The pattern

Reported asWhat was actually trueRoot cause
"Research doesn't work"Research succeeded three times; all three were storedThe read picked an arbitrary row from a one-to-many that the model declared one-to-one
"The button does nothing"POST fired, job queued, work completedLoading state cleared ~20ms after the POST, 14s before the result existed
"I can't hear Donna"Replies were generated and publishedThe TTS subscriber was torn down 3ms after subscribing; nothing was listening
"Donna doesn't respond"Agents ran correctly and had nothing to sayNo agent handled being addressed directly — silence was correct and looked broken
"The toggle doesn't work"The endpoint round-tripped correctlyThe control's label described state but read as an action
"Nothing on screen"The control was rendered and clickableWhite text on a white card

The common factor: every layer reported health while delivering nothing. Logs were clean. Status codes were 200. Job counters showed complete/0-failed. The system's own view of itself was accurate and useless, because none of it was measuring the thing the user experiences.

34.2 · The one-to-one that wasn't

Meeting.research_brief is declared uselist=False — a one-to-one relationship. The research pipeline inserted a new row on every run. One meeting had accumulated eleven briefs; three of them were successful runs. With no ordering, SQLAlchemy returned an arbitrary one — in practice the oldest, which was the original failure. Every retry worked and the UI kept rendering the first failure.

A second query on the same table used scalar_one_or_none(), which raises on multiple rows. It had not fired yet only because it filters on status = 'completed' and no meeting had two completed briefs — a latent crash waiting for the first meeting researched successfully twice.

Fixed at three levels, deliberately: the pipeline now reuses one row per meeting (restoring the invariant the model always claimed), the relationship carries order_by desc(created_at) so pre-existing duplicates resolve to the newest, and the second query takes .first() over an ordered set. The first fix alone would have left every existing meeting broken; the second alone would have left the data model lying.

34.3 · Optimistic UI without a completion signal

Two buttons shared a bug worth stating as a rule. Both did this: 

setLoading(true);
await apiClient.doTheThing(id);   // returns in ~20ms — the job is queued, not done
setTimeout(fetchMeeting, 3000);   // a guess
setLoading(false);                // in finally — runs immediately

The loading state is cleared when the request completes, not when the work does. For research the screen dropped straight back to the failure it had just been asked to retry. For the summary, measurement settled it: the POST returns in 0s and the summary is ready at 17s — the single refetch at 3s ran fourteen seconds early, every time, so the only way to see a summary was to reload the page manually.

Poll to a terminal state; never guess a durationsimplicity vs honesty
Why
Background work has no fixed duration. A hard-coded delay is a bet against the slowest realistic case, and it loses silently — the user sees the pre-action state and concludes the button is dead.
Beat
WebSocket completion events (the hub already exists and this is the better long-term answer); a longer fixed delay (still a guess, just a slower one); a spinner with no timeout (a spinner that never resolves is its own bug).
Trade-off
Polling costs one request every 2.5s for up to 150s, and the screen must commit to a "working" state rather than continuing to offer the button that was already pressed. Bounded rather than indefinite: on timeout it says the work may still be running and offers a retry, which is honest where an eternal spinner is not.
Revisit when
The meeting hub already carries nudge_created and other events over WebSocket. Emitting summary_ready and research_complete there would remove the polling entirely. That is the right fix; polling is the one that could be verified today.

34.4 · A lifetime that ended at the wrong event

The voice worker held its job open with await ctx.wait_for_participant(). That call returns the moment a participant exists — and one always does, because the agent is dispatched in response to somebody joining. So it returned instantly, finally fired, and the TTS subscriber was torn down about three milliseconds after it subscribed: 

04:35:02.622  [TTS] subscribed to meeting:<id>:speak
04:35:02.622  [TTS] unsubscribed from meeting:<id>:speak

Everything downstream stayed healthy. The dispatcher kept publishing spoken replies to a Redis channel with no subscriber, and Redis pub/sub has no concept of an undelivered message — a publish to nobody is a successful publish. Donna was inaudible with nothing anywhere reporting an error. The job now waits on an actual room-disconnect event.

The same file carried a second instance of the same class: _prewarm was defined inside if __name__ == "__main__", so the forked job subprocess — which re-imports the module by name — could never resolve it and died with AttributeError before accepting a room. And once moved to module scope, it still had to become synchronous: LiveKit calls prewarm_fnc directly rather than awaiting it, so an async def produced a coroutine that never ran and a heartbeat that never started.

34.5 · Correct silence is indistinguishable from failure

The 19 live agents are all observers: they watch the discussion and offer context nobody asked for. That is the right default — a collaborator who interjects constantly is worse than one who stays quiet. It also left a hole that every first-time user falls into. The first thing anyone says to a voice assistant is "can you hear me?", which is not meeting content, so the observer agents correctly produced nothing.

Correct behaviour, indistinguishable from a broken product. The reply_agent closes it — narrowly. It fires only on direct address, answers from meeting context in one or two sentences, and says plainly when it does not know rather than inventing something that sounds right. A confident wrong answer spoken aloud into a real meeting is far more damaging than an admission of ignorance.

The detector bug worth remembering. The question-word pattern matched do against the first two letters of Donna — no word boundary. Every sentence merely mentioning her name registered as a question aimed at her, which would have made Donna interrupt any time somebody referred to her in passing: precisely how an assistant becomes something people mute. The fix models the real grammar — strip the vocative, test what follows — so "Donna, what did we decide?" answers and "Donna flagged that earlier" stays silent.

Replies also bypass the voice_nudges flag and the two-minute cooldown. That gating exists to stop unsolicited interjections into a conversation Donna was not invited into; someone asking her a direct question and waiting is the opposite of that. Being asked something and staying silent reads as broken, not as configured.

34.6 · Viewer-relative data in a shared record

Transcripts showed two speakers — "You" and "Nikhil" — for one person. my_name was read only from the attendee list, and the meeting owner is not normally an attendee of their own meeting, so it came back null and the client persisted the literal string 'You' as the speaker.

That is worse than untidy. A transcript is a shared artifact: every other attendee reading it, and every recipient of the summary email, sees "You" referring to somebody who is not them. Attribution in a shared record must be absolute. The fix falls back past the attendee list to the account itself, and the server now overrides viewer-relative labels (you, me, speaker) with the authenticated user's real name — so a buggy client cannot poison the record.

34.7 · Repetition is a correctness bug, not a cosmetic one

The retrieval agents re-run every dispatch cycle, and a passage relevant to the last utterance is usually still relevant to the next. With no deduplication, one finding became nine cards saying two things at 58–80% confidence. The second genuine finding was buried under repeats of the first, which is worse than showing nothing: the user stops reading the panel.

Nudges now carry a content fingerprint, suppressed within a 15-minute window — scoped per meeting and windowed rather than permanent, because a risk resurfacing half an hour later in a different part of the conversation genuinely is worth raising again. Replies need a different key: an LLM-generated answer is worded differently on each cycle, so hashing the text let one question produce two near-identical spoken replies. They dedupe on the question instead.

Known limit. The fingerprint is exact-text after normalization, so a genuinely reworded restatement of the same finding still gets through. Semantic dedup needs an embedding comparison per nudge — real cost on the hot path — and is worth doing only if it shows up in practice.

34.8 · The rule this chapter argues for

Assert on what the user can observe, not on what the function returned. Every bug here passed its own layer's definition of success. The tests that would have caught them are the ones nobody writes: does the control have contrast against its background; does the loading state outlive the request; does the subscriber outlive its subscribe; does the read return the row the write produced; does the label mean the same thing to a second reader.

Two habits came out of this that generalise. First, measure the thing before choosing a constant — "the summary takes 17 seconds" turned a guessed 3-second delay into a justified 150-second bound. Second, when a user says a feature is broken, check whether it is instead invisible; six times out of six here, the backend was fine and the failure was between the result and the person.
